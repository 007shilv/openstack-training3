# 第13章 使用智能体部署与运维 OpenStack

## 学习目标

完成本章学习后，学习者应能够：

1. 解释第二篇人工部署与本章智能体部署的边界；
2. 编写包含目标、事实、约束、验收和清理要求的任务提示词；
3. 监督智能体按17阶段顺序一次性调用 `openstack-ts` 完成平台部署；
4. 使用 CLI/API 对服务、端点、网络、计算和存储进行独立验收；
5. 让智能体完成资源创建、监控诊断、服务恢复、容量分析、日志归档和配置备份；
6. 对删除、磁盘初始化和服务中断等高风险动作实施人工确认；
7. 形成包含提示词、计划、证据、回滚和反思的实训报告。

## 13.1 自动化例外与实验边界

本章是全书唯一允许“智能体读取并调用安装脚本，一次性完成 OpenStack 部署”的章节。第二篇的安装教学仍然全部采用人工方式。本章之所以可以自动化，是因为学习者已经理解每个组件的数据库、身份、配置、同步、启停和验证过程，且 `openstack-ts` 已经过独立测试。

表13-1说明两篇的分工。

**表13-1 第二篇人工部署与第三篇智能体部署的分工**

| 项目 | 第二篇 | 第三篇第13章 |
| --- | --- | --- |
| 目的 | 学会原理和逐步配置 | 学会监督智能体完成复杂任务 |
| 安装方式 | 学生逐条手工输入 | 智能体按批准计划调用已验证脚本 |
| 配置文件 | 学生使用 `vi` 手工编辑 | 由受控脚本生成，智能体核对差异 |
| 数据库与端点 | 学生逐条创建 | 脚本执行，智能体检查结果 |
| 验收 | 学生手工检查 | 智能体检查后，学生再独立验证 |
| 风险责任 | 操作者承担 | 人机共同执行，但最终责任仍由人承担 |

> 重要：本章不能反向证明学生可以跳过第二篇。没有人工部署知识，就无法判断智能体的计划是否漏步，也无法在失败后定位问题。


## 13.3 让智能体形成17阶段部署计划

根据 `openstack-ts`，完整跨节点顺序如下。

**表13-3 OpenStack 双节点17阶段部署顺序**

| 阶段 | 节点 | 脚本 | 里程碑 |
| ---: | --- | --- | --- |
| 1 | controller | `01-controller-network.sh` | controller 地址和主机名固定 |
| 2 | compute | `02-compute-network.sh` | compute 地址和主机名固定 |
| 3 | controller | `03-controller-base.sh` | 本地源、SP2兼容仓库、时间同步 |
| 4 | compute | `04-compute-base.sh` | 计算节点基础环境完成 |
| 5 | controller | `05-controller-services.sh` | MariaDB、RabbitMQ、Memcached、客户端可用 |
| 6 | controller | `06-controller-keystone.sh` | 身份服务和管理员环境可用 |
| 7 | controller | `07-controller-glance.sh` | 镜像 API 可用 |
| 8 | controller | `08-controller-placement.sh` | Placement API 可用 |
| 9 | controller | `09-controller-nova.sh` | Nova 控制面可用 |
| 10 | compute | `10-compute-nova.sh` | nova-compute 与资源提供者可见 |
| 11 | controller | `11-controller-neutron.sh` | Neutron 控制面可用 |
| 12 | compute | `12-compute-neutron.sh` | 双节点 Linux bridge agents 在线 |
| 13 | controller | `13-controller-cinder.sh` | Cinder API 与调度器可用 |
| 14 | compute | `14-compute-cinder.sh` | `/dev/sdb` 成为 Cinder LVM 后端 |
| 15 | controller | `15-controller-swift.sh` | Swift 代理和单副本 ring 完成 |
| 16 | compute | `16-compute-swift.sh` | `/dev/sdc` XFS 存储服务完成 |
| 17 | controller | `17-controller-horizon.sh` | `/dashboard/` 登录页可用 |

依赖关系比“两个节点各自从头跑到尾”更重要。例如，计算节点 Nova 必须在控制面和 Placement 之后；Neutron 控制面先于计算节点 agent；Cinder 和 Swift 都先完成控制面，再初始化对应数据盘；Horizon 最后安装。

## 13.4 一次性部署提示词与执行监督

### 13.4.1 总任务提示词

```text
在我批准你的计划后，请依据当前工作区经过验证的 openstack-ts 脚本，
一次性完成双节点 OpenStack 2023.1 Antelope 部署。

必须使用17阶段跨节点顺序。凭据从受保护的交互或运行时环境获取，
不得回显、写入项目或保存在报告。远程连接必须使用已核对的主机公钥。
每阶段先说明节点、脚本、依赖、预计改动和验证，再执行；返回码非0立即停止。

阶段14只能初始化 compute:/dev/sdb，阶段16只能初始化 compute:/dev/sdc；
每次都重新确认主机地址、根盘祖先、50 GiB容量、无分区/挂载/签名和目标用途，
向我显示脱敏证据并等待明确确认。任何情况下不得写 /dev/sda。

每完成一个组件，只做轻量验收：相关服务 active/enabled、API正常、
一个代表性CLI或最小功能测试。部署结束后生成脱敏验收报告，
包括版本、服务、端点、计算服务、网络代理、卷服务、Swift健康检查和Horizon登录页。
```

### 13.4.2 监督原则

- 不批准只写“我会安装 OpenStack”的空泛计划；
- 不允许智能体调整 IP、磁盘或组件顺序来“绕过错误”；
- 不因某阶段耗时较长而并行执行有依赖的后续阶段；
- 不接受以 `|| true` 掩盖关键失败；
- 只在阶段里程碑截图，不机械截取每条命令；
- 失败时保存返回码、服务状态和末尾日志，停止在故障点。

### 13.4.3 独立人工验收

智能体完成后，学习者在 controller 手工执行代表性查询：

```bash
source /root/admin-openrc
openstack service list
openstack endpoint list --region RegionOne
openstack compute service list
openstack network agent list
openstack volume service list
curl --noproxy '*' -fsS http://controller:8080/healthcheck
curl --noproxy '*' -sS -o /dev/null -w '%{http_code}\n' \
  http://controller/dashboard/auth/login/
```

在 compute 手工确认：

```bash
systemctl is-active openstack-nova-compute neutron-linuxbridge-agent \
  openstack-cinder-volume openstack-swift-account \
  openstack-swift-container openstack-swift-object
pvs --noheadings -o pv_name,vg_name
findmnt /srv/node/sdc
```

只有 API、服务和一个代表性操作均正常，才把部署标记为 PASS。

## 13.5 运维任务的统一方法

后续任务统一采用 `book-` 前缀。智能体必须在创建资源后记录精确 ID，验证时按 ID 查询，清理时按依赖逆序删除。每个任务遵循“提示词—计划—执行—验证—清理/回滚—截图”的结构。

### 任务1：平台服务与端点巡检

**提示词模板**

```text
只读巡检 OpenStack 平台。检查服务目录和三类端点、Nova compute、
Neutron agents、Cinder services、Swift healthcheck、Horizon 登录页。
输出异常项、证据命令和时间戳；不要重启服务，不创建资源。
```

**验证**：手工复核 `openstack service list`、`endpoint list`、`compute service list`、`network agent list` 和 `volume service list`。  
**回滚/清理**：只读任务无需回滚；删除临时输出中的令牌。

**提示词模板**


**回滚/清理**：调整失败执行 revert resize；确认后可 resize confirm。删除只按指定实例 ID。

## 13.8 素养拓展：负责任地使用智能体，练就数字工匠精神

自主可控并不等于把国外工具简单替换为国内工具，也不等于把人的责任交给模型。openEuler、OpenStack、TRAE 和 DeepSeek 的组合体现了开源协作、国产基础软件生态和工程实践的结合。学习者既要看到国产平台持续进步，也要尊重全球开源社区的贡献，用开放、严谨的态度参与技术创新。

数字工匠精神体现在每一次核对中：不把猜测写成事实，不把“无报错”当作成功，不隐藏失败，不越过磁盘和数据安全底线。智能体可以提高速度，但最终批准、验收和责任仍属于人。面对可自动化的工作，职业能力不再只是记住命令，而是能够定义目标、设置边界、判断证据、处理异常并持续改进。

**思考题**：如果智能体给出了看似合理但会初始化错误磁盘的计划，操作者批准后造成数据损失，责任应如何划分？团队应怎样通过技术和制度减少这类风险？

## 本章小结

本章把智能体用于一次性部署和持续运维，但始终保持人工监督与独立验收。一次性部署严格遵循17阶段跨节点顺序，Cinder 与 Swift 的磁盘初始化设置二次确认。运维任务覆盖身份与配额、镜像、规格、网络、路由、安全、实例、浮动 IP、卷、对象、快照、调整、巡检、故障诊断、服务恢复、容量、日志、备份和清理。高质量智能体任务必须同时包含目标、事实、边界、步骤、验证和回滚。
