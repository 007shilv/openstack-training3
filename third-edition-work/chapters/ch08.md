# 第8章 Nova计算服务

## 学习目标

掌握 Nova API、Scheduler、Conductor、noVNC Proxy、Compute 和 Cell v2 的职责；按控制节点后计算节点的顺序，手工完成三库九授权、Nova 身份对象、双节点 `nova.conf`、数据库同步与 Cell 创建；稳定 `compute_id`，手工启动 libvirt 和 nova-compute，发现主机并验证 Placement 资源上报。

## 8.1 Nova架构与构建顺序

### 8.1.1 Nova核心进程与调用关系

`nova-api` 承接 REST 请求，Scheduler 选主机，Conductor 代理计算节点访问数据库，`nova-compute` 调用 libvirt/QEMU 执行虚拟机动作，noVNC Proxy 为浏览器转发控制台。如图8.1所示，API 的快速响应不代表实例已创建，长任务依赖 RabbitMQ 分发。

### 8.1.2 Cell v2架构

`nova_api` 库保存 API、配额、Cell/Host Mapping；`nova_cell0` 保存未能调度到主机的实例；`nova` 作为 cell1 业务库。cell0 UUID 固定为全零，cell1 使用非零 UUID。

### 8.1.3 控制节点和计算节点部署顺序

先建控制面数据库、身份、配置、Cell 和 API；再在 compute 安装 QEMU/libvirt/nova-compute；最后才发现主机并核对 Placement。在任一阶段都不创建镜像、规格、网络或实例。

### 8.6.3 QEMU教学模式与KVM生产模式

实验虚拟机中无 vmx/svm 和 `/dev/kvm`，因此使用 `virt_type=qemu`；优点是可在普通学生设备上复现，缺点是性能较低。生产环境应使用 KVM 并验证硬件加速。

## 8.9 故障处理、素养拓展与总结

### 8.9.1 Cell、计算服务和资源上报故障

- compute 不出现：检查 RabbitMQ、Keystone、Placement、`my_ip` 和 nova-compute 日志。
- 服务出现但无 Host Mapping：执行 `discover_hosts --by-service`，不直接改数据库。
- provider 无库存：查 Placement 认证、虚拟化驱动和节点资源探测。
- cell 部分状态：先 `list_cells`和核对数据库，不通过重复 `create_cell` 碰运气。

### 8.9.2 素养拓展：配置精度、反复验证与工匠精神

Nova 配置涉及多个 URL、IP、用户和密码语义，一个斜杠或一个节名错误都会沿消息链放大。工匠精神不是无限重试，而是每改一步就用可观测证据校验，在未知状态停下来，将经验沉淀为可复现的规范。
