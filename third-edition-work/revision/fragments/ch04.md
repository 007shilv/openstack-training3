# 第四章 openEuler与信创OpenStack实验环境准备

本章导读：本章先认识openEuler的项目发展、社区治理、版本维护和软件生态，再说明本书双节点实验环境的网络与存储分工。随后，我们沿用第二版教材“前提环境—涉及节点—实训目标—步骤详解”的学习路径，逐项完成OpenStack安装前的基础配置。

实验环境准备不是把若干命令简单排列起来。主机名、管理地址、Provider网卡、软件仓和时间服务之间存在先后依赖，任何一项边界不清，都会影响后续组件安装。因此，每一步操作之前都要先理解它解决的问题，再在指定节点完成配置。

## 4.1 openEuler与信创云平台

openEuler社区于2019年末正式成立，2021年11月贡献给开放原子开源基金会。现行项目群制度由openEuler委员会承担重大业务决策，技术委员会负责技术方向，项目群办公室负责日常执行，并通过SIG和Maintainer机制组织具体协作。

这种治理方式说明，openEuler既有企业发起和早期投入的历史，也应当按照基金会框架下的开源社区项目来理解。社区中的需求讨论、代码贡献、软件包维护和版本发布由多方共同参与，不能把它简单等同于某一家企业的内部产品。

从时间线看，openEuler在2019年9月宣布于当年年底开源，社区基础设施随后启用；2021年的基金会贡献又使治理关系进一步清晰。认识这段过程，有助于区分项目起源、当前归属和实际贡献主体，避免用一个静态标签概括不断发展的社区。

SIG是社区围绕某一技术方向组织协作的重要方式。参与者可以在公开规则下讨论需求、维护软件包、改进文档并处理兼容问题。对学习者而言，阅读SIG资料不仅是寻找安装说明，也是在观察一个大型开源项目怎样分配责任、形成技术决策。

openEuler 24.03 LTS是一个长期支持版本族。按照现行规则，LTS版本族与其中的SP有不同维护周期：LTS按全面支持、维护支持等阶段演进，SP则按发布时间和维护计划提供阶段性更新。单个SP不能直接套用整个LTS版本族的年限。

现行规则把LTS版本族的支持分为全面支持和维护支持等阶段，生命周期结束前还可以由联合维护团队申请可选延长。SP在版本族内部承担阶段性特性集成和维护交付，6月与12月发布的SP原则上具有不同周期。阅读版本信息时，应同时看版本族和具体SP。

SP3于12月发布，结合现行规则和官方版本表，可以把它理解为24.03 LTS版本族中的“大SP”。这种判断来自生命周期规则与发布日期的合并，而不是名称本身。教材采用SP3，主要考虑实验软件组合、课程周期和环境复现，不把发布时间直接等同于教学价值。

本书选用openEuler 24.03 LTS SP3。该版本于2025年12月发布，官方计划维护至2027年12月，并采用Linux 6.6内核基线。截至2026年7月，24.03 LTS版本族已经发布SP4，因此教材选择SP3是为了固定实验组合，不表示它是当时版本族中最近发布的SP。

openEuler采用RPM软件包体系。RPM负责软件包格式、安装记录和本地软件包信息，DNF负责访问软件仓、解析依赖并组织安装事务。后续实训使用DNF从指定仓安装软件，使软件来源与节点角色保持一致。

RPM与DNF处在相互关联但职责不同的层次。RPM能够处理单个本地软件包及其元数据，DNF则在软件仓范围内计算依赖关系，并把多个软件包安装组织为事务。云平台组件依赖较多，本书优先用DNF完成安装，减少人工拼接依赖链带来的遗漏。

软件仓不仅是一个下载地址，还包含软件包集合、仓元数据、架构目录和更新节奏。相同软件名在不同发行版本或架构下可能对应不同构建，不能只根据文件名混用。固定仓标识和baseurl，实质上是在固定课堂中软件供应链的入口。

openEuler社区面向服务器、云、边缘和嵌入式等场景开展适配，并提供x86_64、AArch64等架构的发行介质；官方仓中还可看到部分LoongArch64、RISC-V等架构产物。不同架构与场景的成熟度并不完全相同，实际应用应以具体版本介质、硬件兼容清单和应用适配结果为准。

“支持某种架构”也可能表示不同层次：有的架构提供服务器DVD与虚拟机镜像，有的主要面向嵌入式或特定仓目录。只有把处理器架构、发行介质、设备型号和使用场景放在一起，才能形成可执行的选型结论，不能用网站中的总括名称替代兼容范围。

在云平台课堂中，多架构生态的价值首先体现在方法训练。学生需要知道软件包如何按架构构建、镜像如何与计算节点匹配，以及硬件兼容信息为何要落实到具体版本。即使本书虚拟机统一使用x86_64，这套判断方法仍可迁移到其他教学设备。

开源操作系统由Linux内核、系统工具、语言运行环境和大量上游项目共同组成。openEuler一方面吸收并维护上游开源成果，另一方面通过补丁、软件包和适配工作向相关社区反馈；OpenStack SIG则围绕OpenStack在openEuler上的构建、适配和文档开展协作。

这种上下游协作使学习者能够在国内基金会孵化的开源社区环境中理解软件供应链、多架构适配和云平台集成，为建设可信的本土数字基础设施形成实践认识。不过，开源项目身份本身不等于安全认证、合规结论或对所有软硬件的无条件替代承诺。

这里所说的“可信”，强调来源可追溯、规则可理解、变更可管理和责任可说明，而不是给某个系统作无条件安全保证。生产项目还需要核对漏洞响应、维护期限、硬件认证、服务合同和组织自身的安全制度，课堂环境只能帮助建立这些意识。

openEuler是操作系统项目，OpenStack是云基础设施管理平台，二者位于不同软件层次。openEuler为OpenStack组件提供运行环境和软件包基础，OpenStack则在操作系统之上组织计算、网络与存储资源。把两者分开理解，才能看清系统问题与云服务问题的边界。

openEuler社区与OpenInfra、OpenStack社区开展技术交流和适配协作，但这种合作不表示项目隶属关系，也不能由此推出某个SP已经获得特定认证或商业支持。具体OpenStack版本的可用范围，仍应查看目标系统对应的软件仓和SIG资料。

本书操作系统固定为openEuler 24.03 LTS SP3，OpenStack软件包仍固定为Antelope 2023.1。前者提供较新的系统与Linux 6.6内核基线，后者是已经完成部署参数固化的教学组合。Antelope在2026年已经停止社区维护，仅用于隔离实验，不作为新建生产云的版本建议。

SP3默认生成的Antelope软件仓路径没有对应软件包，而openEuler 24.03 LTS SP2仓仍保存所需Antelope内容。因此，本章会把Antelope仓地址改指SP2目录。这只是软件仓兼容处理，不会把已安装的SP3操作系统降级为SP2。

这一组合还体现了教材环境与社区发展快照的区别。社区版本会继续演进，教材实训则要在一个学期内保持地址、软件包和操作步骤稳定。教师应在开课前准备离线仓并保留来源记录，学生则在固定组合中学习组件关系，不把课堂版本误认为生产选型结论。

## 4.2 双节点实验环境与终端工具

本书采用controller与compute两个节点。controller管理地址为192.168.234.151/24，主机名为controller；compute管理地址为192.168.234.150/24，主机名为compute。两台主机的网关和DNS均为192.168.234.2。

双节点不是OpenStack生产架构的规模建议，而是为了用尽量少的主机呈现控制面与资源面的分工。controller集中承载后续数据库、消息系统和各服务控制进程，compute承载虚拟化与资源代理。节点数量减少了，但组件职责并没有因此合并成一个整体。

管理地址采用同一24位前缀，使两个节点能够在192.168.234.0/24管理网中直接通信。网关和DNS使用同一地址，便于虚拟化平台提供外部解析与必要的上游访问。地址规划在课程开始前固定，后续章节不再临时更换。

每个节点配置两块网卡。ens33连接管理网络，承担节点管理和OpenStack控制通信；ens34连接Provider网络，保持链路接通但不配置IP地址。后续Neutron会把ens34接入外部网络，不能提前把它当作第二块管理网卡使用。

管理网络上的流量包括远程终端、组件间接口调用和基础服务通信。把这些流量集中到ens33，可以让主机自身的管理地址保持稳定。Provider网络则用于把云实例网络连接到外部二层环境，两类网络的对象和责任不同。

ens34保持无地址，并不表示它没有作用。网卡仍要连接到正确的虚拟交换网络，后续网络代理会把它作为物理网络接口使用。如果在ens34上保留管理地址或默认路由，可能造成主机流量选路混乱，也会模糊Provider网络的教学边界。

compute的系统盘为/dev/sda，另有/dev/sdb和/dev/sdc两块50 GiB数据盘；/dev/sdb用于Cinder，/dev/sdc用于Swift。两块数据盘在本章不分区、不格式化。controller不需要增加教学数据盘，避免把计算节点的存储角色错误复制到控制节点。

系统盘与数据盘必须分离。/dev/sda保存openEuler和节点软件，后续存储实训只处理两块指定数据盘。这样即使重做Cinder或Swift实验，也不会把系统卷误当成存储后端。设备名称和容量是后续操作必须共同满足的条件。

Cinder面向块存储，Swift面向对象存储，两者的数据组织方式不同。为它们分别预留整盘，可以让学生在后续章节直接观察块设备、卷组和对象存储设备的差异。两块盘容量相同是课堂标准化安排，不表示生产系统应采用相同容量。

两台虚拟机都是与生产网络隔离、可以恢复初始状态的教学资源。开始实训前应确认虚拟机名称、网卡连接方式和磁盘顺序与本书一致，不把个人文件或真实业务数据放入实验磁盘。

“可以恢复”意味着教师能在课程阶段之间回到规定的初始状态，而不是允许跳过当前步骤。恢复后，主机名、地址、软件仓和服务状态都可能回到旧值，因此应按章节顺序重新完成需要的配置。课堂记录要写清所用初始状态，避免不同小组从不同基础开始。

资源规模可以根据宿主机能力适度调整，但角色边界不应变化。controller需要为多个控制服务预留内存，compute需要支持嵌套虚拟化并承担实例运行。若宿主机资源不足，应减少并发实例或分组使用环境，不能删除必要网卡或混用数据盘来节省资源。

在Windows管理主机上，可以选择Xshell、SecureCRT或Windows PowerShell建立SSH终端连接；三者只承担命令输入与结果显示，本书不展开独立的软件安装和界面操作教程。

## 4.3 实训项目1 openEuler云平台基本环境配置

一、实训前提环境

准备两台已经安装openEuler 24.03 LTS SP3的虚拟机，并按照4.2节连接ens33与ens34。controller应预先具备教师准备的/opt/openstack_repo离线软件仓，compute通过controller提供的只读FTP仓取得相同软件包。

系统安装示例统一把root密码设为qwer1234。该口令只适用于隔离、可重置的教学环境，不得用于校园网、互联网或任何生产系统；真实系统应使用独立强口令、最小权限账户和受控的远程管理策略。

二、实训涉及节点

本实训涉及controller和compute两个节点。命令提示符中的主机名用于提醒当前操作位置，输入命令前应先核对终端所连接的节点，避免把控制节点配置写入计算节点。

三、实训目标

完成双节点主机名、固定管理地址与主机名解析配置；明确ens34的无地址边界；完成隔离教学环境中的SELinux与防火墙调整；建立本地和FTP软件仓；安装Antelope发行包，并启动vsftpd与chronyd基础服务。

四、实训步骤及其详解

步骤一：准备虚拟机和网络适配器

先关闭虚拟机电源，在虚拟化平台中为controller和compute各连接两块网络适配器。ens33所在虚拟网络应能到达网关192.168.234.2，ens34所在虚拟网络用于Provider网络。两块适配器均保持“已连接”和“启动时连接”。

compute保留/dev/sda作为系统盘，再按顺序添加两块50 GiB虚拟磁盘，使其在后续章节分别承担Cinder与Swift数据角色。controller只保留满足系统与控制服务容量需要的系统盘，不添加这两块教学数据盘。

步骤二：设置两个节点的主机名

主机名是服务配置和节点间解析的稳定标识。先在controller设置控制节点主机名，再在compute设置计算节点主机名。

```command
[root@controller ~]# hostnamectl set-hostname controller
```

```command
[root@compute ~]# hostnamectl set-hostname compute
```

步骤三：设置固定管理地址并保持Provider网卡无地址

ens33使用手工IPv4配置。controller写入192.168.234.151/24，compute写入192.168.234.150/24；两台节点都把192.168.234.2设置为网关和DNS，并让连接随系统启动。

```command
[root@controller ~]# nmcli connection modify ens33 ipv4.addresses 192.168.234.151/24 ipv4.gateway 192.168.234.2 ipv4.dns 192.168.234.2 ipv4.method manual connection.autoconnect yes
[root@controller ~]# nmcli connection up ens33
```

```command
[root@compute ~]# nmcli connection modify ens33 ipv4.addresses 192.168.234.150/24 ipv4.gateway 192.168.234.2 ipv4.dns 192.168.234.2 ipv4.method manual connection.autoconnect yes
[root@compute ~]# nmcli connection up ens33
```

Provider网络只需要二层连接，因此ens34不配置IP地址。下面清除IPv4地址、网关和DNS，并关闭IPv4、IPv6协议配置，但保留连接自动启用。

```command
[root@controller ~]# nmcli connection modify ens34 ipv4.addresses "" ipv4.gateway "" ipv4.dns "" ipv4.method disabled ipv6.method disabled connection.autoconnect yes
[root@controller ~]# nmcli connection up ens34
```

```command
[root@compute ~]# nmcli connection modify ens34 ipv4.addresses "" ipv4.gateway "" ipv4.dns "" ipv4.method disabled ipv6.method disabled connection.autoconnect yes
[root@compute ~]# nmcli connection up ens34
```

步骤四：配置双节点主机名解析

后续服务配置会反复使用controller和compute名称。分别使用vi打开两个节点的/etc/hosts，保留文件中原有内容，只在文件末尾追加后两行地址映射，使主机名含义在两台节点上保持一致。下面同时列出openEuler默认的本地主机条目，便于读者辨认追加位置。

```command
[root@controller ~]# vi /etc/hosts
```

```command
[root@compute ~]# vi /etc/hosts
```

```config
127.0.0.1   localhost localhost.localdomain localhost4 localhost4.localdomain4
::1         localhost localhost.localdomain localhost6 localhost6.localdomain6
192.168.234.151 controller
192.168.234.150 compute
```

步骤五：调整隔离教学环境的安全控制

OpenStack各组件的细粒度安全策略会在后续章节逐步引入。为了使固定实验组合便于教学，本章暂时把SELinux改为permissive，并停止firewalld。这不是通用部署规范，生产环境必须围绕网络分区、端口、访问控制和强制访问策略单独设计安全方案。

在两个节点使用vi打开/etc/selinux/config，把SELINUX参数改为permissive。配置文件决定下次启动后的模式，setenforce 0则使当前运行环境进入宽容模式。

```command
[root@controller ~]# vi /etc/selinux/config
```

```command
[root@compute ~]# vi /etc/selinux/config
```

```config
SELINUX=permissive
```

```command
[root@controller ~]# setenforce 0
[root@controller ~]# systemctl disable firewalld
[root@controller ~]# systemctl stop firewalld
```

```command
[root@compute ~]# setenforce 0
[root@compute ~]# systemctl disable firewalld
[root@compute ~]# systemctl stop firewalld
```

步骤六：配置本地与FTP软件仓

controller直接读取/opt/openstack_repo中的仓数据。使用vi创建/etc/yum.repos.d/openstack-local.repo，仓标识统一为openstack-local，后续安装命令据此限定软件来源。

```command
[root@controller ~]# vi /etc/yum.repos.d/openstack-local.repo
```

```config
[openstack-local]
name=OpenStack Local Repository
baseurl=file:///opt/openstack_repo
enabled=1
gpgcheck=0
```

compute通过controller的FTP服务读取同一目录。仍使用vi创建同名仓配置，但把baseurl改为controller管理地址上的FTP路径。

```command
[root@compute ~]# vi /etc/yum.repos.d/openstack-local.repo
```

```config
[openstack-local]
name=OpenStack Local Repository
baseurl=ftp://192.168.234.151/openstack_repo
enabled=1
gpgcheck=0
```

这里的gpgcheck=0只服务于来源固定、网络隔离且可重置的课堂软件仓。生产系统必须恢复软件包签名检查，保护仓元数据和传输链路，并建立软件来源、更新审批和制品留存制度，不能照搬这一教学简化设置。

步骤七：在controller提供只读FTP仓

先从openstack-local安装vsftpd，再使用vi编辑/etc/vsftpd/vsftpd.conf。匿名用户只能读取以/opt为根的仓内容，不能使用本地账户登录，也不能向服务器写入文件。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo=openstack-local install vsftpd
[root@controller ~]# vi /etc/vsftpd/vsftpd.conf
```

```config
listen=YES
listen_ipv6=NO
anonymous_enable=YES
local_enable=NO
write_enable=NO
anon_root=/opt
no_anon_password=YES
hide_ids=YES
dirmessage_enable=YES
use_localtime=YES
xferlog_enable=YES
connect_from_port_20=YES
pasv_enable=YES
pasv_min_port=30000
pasv_max_port=30009
```

配置保存后，先设置vsftpd随系统启动，再启动当前服务。至此，compute的软件仓地址具备了读取基础。

```command
[root@controller ~]# systemctl enable vsftpd
[root@controller ~]# systemctl start vsftpd
```

步骤八：安装Antelope发行包并调整兼容仓地址

openstack-release-antelope负责提供Antelope仓配置。两个节点都只从openstack-local安装该发行包，避免安装过程提前访问尚未修正的外部Antelope仓。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo=openstack-local install openstack-release-antelope
```

```command
[root@compute ~]# dnf -y --disablerepo='*' --enablerepo=openstack-local install openstack-release-antelope
```

发行包生成/etc/yum.repos.d/openstack-antelope.repo后，分别使用vi打开该文件，把软件包路径中的openEuler-24.03-LTS-SP3改为openEuler-24.03-LTS-SP2。下面保留主仓和更新仓的必要参数。

```command
[root@controller ~]# vi /etc/yum.repos.d/openstack-antelope.repo
```

```command
[root@compute ~]# vi /etc/yum.repos.d/openstack-antelope.repo
```

```config
[OpenStack_Antelope]
name=OpenStack_Antelope
baseurl=https://repo.openeuler.org/openEuler-24.03-LTS-SP2/EPOL/multi_version/OpenStack/Antelope/$basearch/
enabled=1
gpgcheck=1
gpgkey=https://repo.openeuler.org/openEuler-24.03-LTS-SP2/OS/$basearch/RPM-GPG-KEY-openEuler
priority=1

[OpenStack_Antelope_update]
name=OpenStack_Antelope_update
baseurl=https://repo.openeuler.org/openEuler-24.03-LTS-SP2/EPOL/update/multi_version/OpenStack/Antelope/$basearch/
enabled=1
gpgcheck=1
gpgkey=https://repo.openeuler.org/openEuler-24.03-LTS-SP2/OS/$basearch/RPM-GPG-KEY-openEuler
priority=1
```

这项修改只改变DNF取得Antelope软件包的位置。系统发行版仍是openEuler 24.03 LTS SP3，内核和基础系统包不会因为仓路径中出现SP2而自动降级。后续章节仍按SP3系统环境解释服务配置。

步骤九：按顺序安装并启动时间服务

OpenStack控制面与计算节点需要一致的时间基础。本书沿用openEuler中chrony的默认上游时间源，不把controller改造成未经实验固化的NTP服务器。先在controller安装并启动chronyd，再处理compute。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo=openstack-local install chrony
[root@controller ~]# systemctl enable chronyd
[root@controller ~]# systemctl start chronyd
```

controller启动完成后，在compute执行相同的软件安装与服务启动。操作到服务启动即结束，不在本章增加状态查询或安装后检查命令。

```command
[root@compute ~]# dnf -y --disablerepo='*' --enablerepo=openstack-local install chrony
[root@compute ~]# systemctl enable chronyd
[root@compute ~]# systemctl start chronyd
```

完成上述步骤后，双节点已经具备后续组件安装所需的主机身份、管理网络、软件仓和时间服务基础。OpenStack命令行客户端与各控制面依赖将在第五章随基础服务一起安装，避免本章越过环境准备的教学边界。
