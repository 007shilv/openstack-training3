# 第四章 openEuler与信创OpenStack实验环境准备

本章导读：OpenStack运行在Linux操作系统之上，节点的主机名、网络、软件仓和时间状态会直接影响后续组件之间的通信。本章先介绍openEuler及其在信创云基础设施中的位置，再说明双节点实验环境的网络、磁盘和组件分工，最后完成OpenStack安装前的基础配置。

## 4.1 openEuler与信创云平台

一．openEuler操作系统

1．项目发展与社区治理

openEuler是面向数字基础设施的开源操作系统，应用范围包括服务器、云计算、边缘计算和嵌入式系统。操作系统由Linux内核、系统工具、软件包管理、语言运行环境和大量上游开源项目共同构成，为数据库、中间件、虚拟化和云平台组件提供统一运行基础。

openEuler社区于2019年末成立，2021年贡献给开放原子开源基金会。社区通过委员会、技术委员会、特别兴趣组和维护者机制组织技术协作。需求讨论、软件包维护、缺陷修复和版本发布由社区参与者按照公开流程共同完成，项目治理与某一家企业的内部产品管理存在区别。

特别兴趣组围绕内核、虚拟化、云原生、OpenStack、存储和安全等方向组织工作。OpenStack相关软件包的构建、依赖适配和使用资料由相应社区团队持续维护。社区协作使操作系统、硬件和上层软件之间形成公开的适配关系，也为云平台在不同处理器架构上的运行提供基础。

openEuler采用RPM软件包体系。RPM负责软件包格式、安装记录和本地软件信息，DNF负责访问软件仓、解析依赖并组织安装事务。OpenStack组件依赖的软件较多，通过统一软件仓安装可以保持包来源、体系结构和版本关系一致。

2．长期支持版本与服务包

openEuler版本包括创新版本和长期支持版本。长期支持版本以较长维护周期面向服务器和生产基础设施，服务包在长期支持版本族中集成硬件支持、缺陷修复和软件更新。判断一个系统的维护状态时，需要同时识别版本族和具体服务包。

本书实验环境采用openEuler 24.03 LTS SP3。该版本使用Linux 6.6内核基线，能够为本书选定的OpenStack软件包提供稳定运行环境。教材中的操作均以这一固定组合为准，从而使各章的命令、配置文件路径和服务名称保持一致。

OpenStack采用2023.1 Antelope软件包。选择这一版本的主要原因是它与openEuler 24.03 LTS SP3上的软件包和配置组合较为稳定，适合在实验环境中连续完成身份、镜像、计算、网络和存储组件的安装。产业技术现状仍以第三章介绍的OpenStack社区版本为准。

二．信创OpenStack技术栈

1．从硬件到云服务的分层

信创云平台不是单个软件产品，而是处理器、服务器、网络存储设备、操作系统、云平台和上层应用共同组成的技术体系。各层之间通过指令集、驱动、系统调用、软件包、服务接口和数据格式连接，任何一层的变化都可能影响相邻层的兼容关系。

图4.1给出了本书所涉及的信创OpenStack技术栈。图中最下层是处理器、服务器、网卡和磁盘等硬件资源；openEuler位于操作系统层；KVM、libvirt、Linux网络与逻辑卷管理构成资源虚拟化基础；OpenStack服务把计算、网络和存储能力转化为云资源；最上层由Horizon、命令行和应用接口向使用者提供访问入口。

{{FIGURE:图4.1}}

图4.1中的各层具有清楚的职责。硬件层提供物理容量，操作系统管理设备和进程，虚拟化层形成可分配资源，OpenStack控制资源的申请与生命周期，访问层面向人员和程序。平台问题可以沿着这一层次定位：设备识别属于操作系统和驱动范围，实例调度属于OpenStack控制服务范围，两者不能混为同一故障。

2．开源适配与平台自主性

openEuler与OpenStack都采用开放源代码方式发展。开放代码使平台建设者能够理解组件关系、检查接口并进行软硬件适配，但可见源代码并不自动等于任意组合均可使用。具体环境仍要核对处理器架构、系统版本、软件仓、驱动和组件依赖。

信创化平台强调关键基础软件的适配、维护和替换能力。系统建设不仅关注软件能否安装，还要关注升级、漏洞修复、数据迁移、故障恢复和长期运行。实验环境通过固定版本与双节点拓扑呈现最基本的组件关系，生产环境还需要增加高可用、容量规划、安全控制和运行保障。

## 4.2 双节点实验环境与终端工具

一．双节点总体拓扑

1．控制节点与计算节点

本书采用controller和compute两个节点。controller的管理地址为192.168.234.151/24，承担数据库、消息队列、缓存和各OpenStack控制服务；compute的管理地址为192.168.234.150/24，承担虚拟机运行以及网络、块存储和对象存储代理。两个节点均安装openEuler 24.03 LTS SP3。

图4.2表示双节点实验环境的总体连接。管理主机通过管理网络连接controller和compute，两个节点再通过Provider网络连接外部二层网络。控制节点向计算节点提供身份、镜像、调度和网络控制，计算节点向控制服务报告资源状态并执行实例、网络和存储任务。

{{FIGURE:图4.2}}

图4.2中的双节点是按职责划分的最小实验拓扑。控制服务集中在controller，便于观察服务之间的调用；资源执行进程集中在compute，便于区分控制面与资源面。生产环境通常设置多个控制节点、多个计算节点和独立存储系统，以降低单点故障影响并扩展容量。

表4-1列出了两个节点的基础配置。处理器和内存可以根据宿主机能力适当增加，主机名、管理地址、网卡角色和数据盘分工则在后续章节保持不变。

{{TABLE:表4-1}}

表4-1中，controller不配置Cinder和Swift实验数据盘；compute除系统盘外增加两块50 GiB数据盘。节点资源可以扩容，但不能交换地址或把计算节点的数据盘配置到控制节点，否则后续服务参数将与实际角色不一致。

二．双网卡与网络平面

1．管理网络

ens33连接管理网络192.168.234.0/24。controller使用192.168.234.151，compute使用192.168.234.150，网关和域名解析服务器均为192.168.234.2。远程终端、数据库连接、消息传递和OpenStack服务接口主要通过管理网络通信。

管理地址必须保持固定。OpenStack配置文件、数据库授权和服务端点会引用controller名称或管理地址，如果节点通过动态地址发生变化，服务之间将无法按照原配置建立连接。主机名与地址映射写入两个节点的/etc/hosts，使内部通信不依赖外部域名解析。

2．Provider网络

ens34连接Provider网络，保持链路启用但不配置IP地址。后续Neutron会把该接口映射到Provider物理网络，使云实例能够通过虚拟交换与外部网络连接。主机自身的管理地址和默认路由仍位于ens33。

图4.3把两块网卡与两个网络平面分开表示。蓝色路径为管理通信，连接终端、服务接口和节点间控制消息；绿色路径为Provider网络数据通信，主要承载实例对外访问。分开设置能够避免主机管理流量与实例数据流量在逻辑上混淆。

{{FIGURE:图4.3}}

图4.3中的ens34虽然没有IP地址，仍然是Provider网络的数据入口。无地址只表示主机不通过该接口建立三层管理连接，并不表示网卡关闭。若ens34误配默认路由，主机访问可能改变出口；若网卡未连接，后续网络服务无法把实例端口接入外部网络。

表4-2汇总两块网卡的用途和地址设置。后续章节出现管理IP、服务端点或Provider接口时，都可以回到该表确认它们属于哪个网络平面。

{{TABLE:表4-2}}

表4-2中的管理网络同时承担实验环境的控制通信。生产环境可进一步划分管理、API、存储、隧道和外部网络，并为不同流量设置带宽、冗余与访问控制；本书双网卡拓扑保留了最关键的管理面与Provider数据面差异。

三．磁盘与组件分工

1．系统盘和数据盘

两个节点的/dev/sda均为系统盘，用于安装openEuler和OpenStack软件。compute额外配置/dev/sdb与/dev/sdc两块50 GiB整盘：/dev/sdb在Cinder章节建立逻辑卷后端，/dev/sdc在Swift章节建立XFS对象存储设备。本章不对两块数据盘进行分区或格式化。

表4-3列出了磁盘角色。磁盘名称、容量和用途共同构成后续存储操作的边界，不能只凭“第二块磁盘”判断设备。每次涉及初始化磁盘时，都需要先核对节点、设备名、容量、挂载和已有签名。

{{TABLE:表4-3}}

表4-3将Cinder与Swift使用不同磁盘，是因为两种存储模型不同。Cinder把块设备组织为卷并提供给实例，Swift把磁盘目录组织为对象存储设备。分别预留整盘可以在后续章节清楚观察逻辑卷与XFS对象存储目录的差异。

2．组件运行位置

图4.4表示本书第5章以后各组件的运行位置。MariaDB、RabbitMQ、Memcached以及Keystone、Glance、Placement、Nova、Neutron、Cinder、Swift和Horizon的控制服务运行在controller；nova-compute、Neutron代理、cinder-volume和Swift存储服务运行在compute。

{{FIGURE:图4.4}}

图4.4中的控制节点保存云平台状态并接收资源请求，计算节点执行实际资源操作。服务之间通过管理网络连接，Provider网络只在Neutron配置后承载实例外部数据。Cinder和Swift虽在控制节点提供接口，真正的数据后端位于compute的两块数据盘。

四．终端工具

Windows管理主机可以使用Xshell、SecureCRT或Windows PowerShell建立SSH连接。这些工具只负责向Linux节点输入命令并显示结果，选择其中任意一种即可。连接时使用controller或compute的固定管理地址，进入终端后先根据提示符中的主机名确认当前节点。

## 4.3 实训项目1 openEuler云平台基本环境配置

一．实训前提环境

准备两台已安装openEuler 24.03 LTS SP3的虚拟机。两台虚拟机各配置ens33和ens34两块网卡；compute另有/dev/sdb和/dev/sdc两块50 GiB空白磁盘。系统安装时root口令统一设置为qwer1234。

二．实训涉及节点

本实训涉及controller和compute两个节点。命令提示符中的主机名表示操作位置，同一配置分别出现两个提示符时，需要在对应节点各执行一次。

三．实训目标

1．完成controller与compute主机名和固定管理地址配置。

2．完成双节点主机名解析，并保持ens34为无IP地址的Provider接口。

3．完成SELinux、基础网络服务和时间同步配置。

4．完成controller本地软件仓与compute FTP软件仓配置。

5．安装OpenStack Antelope发行包并启动vsftpd与chronyd服务。

四．实训步骤及其详解

步骤一：设置主机名

在controller设置控制节点主机名，在compute设置计算节点主机名。主机名将写入后续服务配置，因此两个节点不能互换。

```command
[root@controller ~]# hostnamectl set-hostname controller
```

```command
[root@compute ~]# hostnamectl set-hostname compute
```

步骤二：配置ens33固定管理地址

controller的ens33写入192.168.234.151/24，compute的ens33写入192.168.234.150/24。两个节点使用相同网关和域名解析服务器，并使连接随系统自动启动。

```command
[root@controller ~]# nmcli connection modify ens33 ipv4.addresses 192.168.234.151/24 ipv4.gateway 192.168.234.2 ipv4.dns 192.168.234.2 ipv4.method manual connection.autoconnect yes
[root@controller ~]# nmcli connection up ens33
```

```command
[root@compute ~]# nmcli connection modify ens33 ipv4.addresses 192.168.234.150/24 ipv4.gateway 192.168.234.2 ipv4.dns 192.168.234.2 ipv4.method manual connection.autoconnect yes
[root@compute ~]# nmcli connection up ens33
```

步骤三：设置ens34为无地址Provider接口

清除ens34上的IPv4地址、网关和域名解析设置，关闭IPv4与IPv6三层配置，同时保持连接自动启用。

```command
[root@controller ~]# nmcli connection modify ens34 ipv4.addresses "" ipv4.gateway "" ipv4.dns "" ipv4.method disabled ipv6.method disabled connection.autoconnect yes
[root@controller ~]# nmcli connection up ens34
```

```command
[root@compute ~]# nmcli connection modify ens34 ipv4.addresses "" ipv4.gateway "" ipv4.dns "" ipv4.method disabled ipv6.method disabled connection.autoconnect yes
[root@compute ~]# nmcli connection up ens34
```

步骤四：配置双节点主机名解析

分别使用vi打开两个节点的/etc/hosts，保留文件原有内容，在末尾加入controller和compute地址映射。

```command
[root@controller ~]# vi /etc/hosts
```

```command
[root@compute ~]# vi /etc/hosts
```

```config
127.0.0.1   localhost localhost.localdomain localhost4 localhost4.localdomain4
::1         localhost localhost.localdomain localhost6 localhost6.localdomain6
192.168.234.151 controller
192.168.234.150 compute
```

步骤五：设置SELinux与防火墙

本书实验环境使用固定的隔离网络。分别使用vi打开两个节点的/etc/selinux/config，把SELINUX设置为permissive，再停止并禁止firewalld随系统启动。

```command
[root@controller ~]# vi /etc/selinux/config
```

```command
[root@compute ~]# vi /etc/selinux/config
```

```config
SELINUX=permissive
```

```command
[root@controller ~]# setenforce 0
[root@controller ~]# systemctl disable --now firewalld
```

```command
[root@compute ~]# setenforce 0
[root@compute ~]# systemctl disable --now firewalld
```

步骤六：配置controller本地软件仓

controller中的OpenStack软件包位于/opt/openstack_repo。使用vi创建/etc/yum.repos.d/openstack-local.repo，写入本地仓地址。gpgcheck参数按本书已准备的离线软件仓设置。

```command
[root@controller ~]# vi /etc/yum.repos.d/openstack-local.repo
```

```config
[openstack-local]
name=openEuler 24.03 LTS SP3 OpenStack Local Repository
baseurl=file:///opt/openstack_repo
enabled=1
gpgcheck=0
```

安装FTP服务，并使用vi打开/etc/vsftpd/vsftpd.conf，把匿名访问根目录设置为/opt，保持匿名用户只读。

```command
[root@controller ~]# dnf --disablerepo='*' --enablerepo=openstack-local install -y vsftpd
[root@controller ~]# vi /etc/vsftpd/vsftpd.conf
```

```config
anonymous_enable=YES
write_enable=NO
anon_root=/opt
```

```command
[root@controller ~]# systemctl enable --now vsftpd
```

步骤七：配置compute的FTP软件仓

在compute使用vi创建相同仓标识，baseurl指向controller提供的只读FTP目录。

```command
[root@compute ~]# vi /etc/yum.repos.d/openstack-local.repo
```

```config
[openstack-local]
name=openEuler 24.03 LTS SP3 OpenStack FTP Repository
baseurl=ftp://controller/openstack_repo
enabled=1
gpgcheck=0
```

步骤八：安装Antelope发行包并修正软件仓路径

在两个节点只启用openstack-local软件仓安装Antelope发行包。安装后使用vi打开Antelope仓配置，把路径中的SP3改为SP2。该修改只改变OpenStack软件包仓地址，不改变已安装的openEuler SP3系统。

```command
[root@controller ~]# dnf --disablerepo='*' --enablerepo=openstack-local install -y openstack-release-antelope
[root@controller ~]# vi /etc/yum.repos.d/openstack-antelope.repo
```

```command
[root@compute ~]# dnf --disablerepo='*' --enablerepo=openstack-local install -y openstack-release-antelope
[root@compute ~]# vi /etc/yum.repos.d/openstack-antelope.repo
```

```config
[OpenStack_Antelope]
name=OpenStack Antelope
baseurl=https://repo.openeuler.org/openEuler-24.03-LTS-SP2/EPOL/multi_version/OpenStack/Antelope/$basearch/
enabled=1
gpgcheck=0

[OpenStack_Antelope_update]
name=OpenStack Antelope Update
baseurl=https://repo.openeuler.org/openEuler-24.03-LTS-SP2/EPOL/update/multi_version/OpenStack/Antelope/$basearch/
enabled=1
gpgcheck=0
```

步骤九：配置时间同步

在两个节点安装chrony。controller作为实验环境的时间源，compute向controller同步。先使用vi修改controller的/etc/chrony.conf，保留原有基础配置并加入允许管理网访问的地址段。

```command
[root@controller ~]# dnf --disablerepo='*' --enablerepo=openstack-local install -y chrony
[root@controller ~]# vi /etc/chrony.conf
```

```config
server 192.168.234.2 iburst
allow 192.168.234.0/24
local stratum 10
```

在compute把时间源设置为controller。

```command
[root@compute ~]# dnf --disablerepo='*' --enablerepo=openstack-local install -y chrony
[root@compute ~]# vi /etc/chrony.conf
```

```config
server controller iburst
```

最后依次启动并设置两个节点的chronyd随系统启动。

```command
[root@controller ~]# systemctl enable --now chronyd
```

```command
[root@compute ~]# systemctl enable --now chronyd
```

至此，双节点主机名、网络、软件仓和时间服务已经配置完成。后续章节按照MariaDB与基础服务、Keystone、Glance、Placement、Nova、Neutron、Cinder、Swift和Horizon的依赖顺序继续安装。
