# 第八章 Placement的安装及其配置

本章导读：本章介绍OpenStack资源管理服务Placement的基本功能、核心对象和调用关系，并在Glance已经完成部署的controller上手工安装和配置Placement。云平台中的计算、内存、磁盘以及加速设备等资源来自不同实体，调度服务需要知道资源在哪里、总量是多少、哪些数量已经被占用、哪些资源具有特定能力。Placement用统一的数据模型记录这些事实，并为Nova Scheduler提供分配候选。

学习Placement可以从Resource Provider、Resource Class、Inventory、Trait和Allocation等基本概念开始。本章在这些概念基础上进一步讲解Consumer、Provider Tree、Aggregate、Generation和Allocation Candidate，使读者能够从“资源有什么”继续理解到“资源由谁提供、被谁占用、调度请求怎样与资源模型匹配”。Placement源于Nova的资源管理需求，后来成为独立服务，但它仍与nova-compute和nova-scheduler保持紧密协作。

本章实训继续采用四段式结构。所有部署操作在controller逐条输入，数据库账户按localhost、127.0.0.1和%三种来源建立，Keystone中的placement用户、admin角色授权、placement服务和三个端点手工创建。配置文件使用vi编辑，本地Antelope软件包附带的空policy.json按实际需要转换为policy.yaml，数据库同步完成后再配置Apache的8778虚拟主机并重新加载服务。

本书把Placement数据库账户和服务用户口令统一写为qwer1234，仅用于无公网入口、无生产数据且可随时重置的隔离教学环境。生产平台必须为不同身份设置独立强口令，限制配置文件访问，并将资源数据的准确性、凭据保护和权限边界纳入日常运维制度。

## 8.1 Placement功能简介

OpenStack需要管理的不只是虚拟机数量。计算节点具有一定数量的虚拟CPU、内存和本地磁盘，部分节点还可能具有GPU、FPGA、特定网卡、SSD或可信执行能力。网络服务可以提供带宽、虚拟接口和地址资源，存储服务可以提供不同后端池的容量。若每个组件用完全不同的方式描述资源，调度器就难以在一次请求中形成一致判断。

Placement是一项通用的资源清单与分配服务。它允许Nova等服务登记资源提供者、资源清单和特征，记录消费者已经占用的数量，并根据请求返回可满足条件的分配候选。Placement维护的是资源事实与占用关系，不负责启动虚拟机，也不直接决定最终选择哪一台计算节点。

在Nova的常见工作过程中，计算节点上的nova-compute通过资源跟踪器把本节点对应的资源提供者、可量化资源和特征写入Placement。控制节点上的nova-scheduler根据实例规格、镜像属性、网络和其他要求，请求一组Allocation Candidate。Scheduler再结合自己的过滤器、权重和调度规则缩小候选范围，Nova随后为选定资源建立Allocation。

这种分工把“记录资源事实”“寻找可满足请求的候选”和“完成最终调度决策”分成不同职责。Placement回答哪些资源组合满足数量、特征、聚合和拓扑要求；Nova Scheduler结合计算服务策略作出最终选择；nova-compute负责实际创建和管理实例。若把Placement直接称为调度器，就会忽略Nova在调度流程中的核心作用。

Placement通过基于HTTP的API提供能力，并采用微版本逐步扩展数据模型和请求语义。服务端与客户端在请求中协商API微版本，使新功能可以在保持既有接口行为的基础上演进。OpenStack升级时，Placement、Nova控制服务和计算节点之间需要考虑兼容顺序，不能只看单个软件包是否已经更新。

一. Resource Provider资源提供者

Resource Provider是实际提供资源的实体。最常见的资源提供者是计算节点，一台compute可以提供VCPU、MEMORY_MB和DISK_GB。资源提供者也可以表示共享存储池、网络设备、GPU、虚拟功能或其他可被工作负载使用的实体。Placement使用UUID唯一识别资源提供者，名称主要用于人员阅读和运维定位。

资源提供者可以组成Provider Tree。根提供者通常表示计算主机，子提供者可以表示主机内部的NUMA节点、PCI设备、GPU或由其他服务管理的资源。树形结构能够表达资源之间的归属和拓扑关系，使调度请求不仅关心“总量够不够”，还可以关心“这些资源是否来自同一棵提供者树或具有指定关系”。

共享资源不一定属于某一台计算主机的子树。例如，一个存储池可以同时服务多台计算节点。Placement可以借助Aggregate把共享提供者与一组计算提供者建立关联。Aggregate在这里是一种关系集合，不直接增加资源数量，也不等同于Nova Host Aggregate中的所有调度属性；使用时要根据所在服务理解它的语义。

资源提供者具有Generation。每当其Inventory、Trait、Aggregate关系或Allocation发生变化时，Generation会随之变化。客户端更新资源时携带所依据的Generation，可以发现自己读取资源之后是否已经发生并发修改。这种并发控制避免较旧的数据无声覆盖较新的资源状态，是分布式控制面保持一致性的重要机制。

二. Resource Class资源类别

Resource Class描述“资源是什么”。Placement定义了VCPU、MEMORY_MB、DISK_GB等标准资源类别，也可以表达SRIOV_NET_VF、VGPU等资源。不同类别采用不同计量单位：VCPU按虚拟处理器数量计数，MEMORY_MB按MiB计数，DISK_GB按GiB计数。调度请求与资源清单只有使用相同类别，才能比较供给和需求。

当标准类别不能描述设备或业务资源时，可以建立以CUSTOM_开头的自定义资源类别。自定义类别应具有明确、稳定的含义，不能把节点名称、临时用途或人员习惯直接当作类别。若不同团队用多个名称表达同一种资源，调度请求就难以形成统一匹配。

Resource Class只说明资源类型，不说明某个提供者有多少资源，也不说明资源质量。数量由Inventory描述，定性能力由Trait描述，已经使用的数量由Allocation描述。把类别、数量、特征和占用拆开，是Placement模型能够支持不同资源的基础。

三. Inventory资源清单

Inventory是某个资源提供者拥有的某类可计量资源。它不仅记录total，还可以记录reserved、min_unit、max_unit、step_size和allocation_ratio。total表示物理或逻辑总量，reserved表示为宿主机或平台保留、不向工作负载分配的数量，allocation_ratio表示资源超分比率。

min_unit和max_unit限定一次分配允许请求的最小值和最大值，step_size限定请求数量的步长。例如，某类资源必须成组分配时，可以通过步长表达。有效容量不是简单把total原样交给调度器，而是结合保留量、超分比率以及当前Allocation计算。参数之间必须相互协调，错误的清单可能使调度器高估或低估资源。

超分允许工作负载声明的资源总量高于物理总量，常用于虚拟CPU等可以分时使用的资源。超分不是凭空产生硬件，过高比率可能造成争用和性能波动。教学环境应先理解公式与对象关系，生产环境则要结合工作负载类型、服务等级和监控数据确定比率。

nova-compute的资源跟踪器会周期性更新计算节点Inventory。管理员不应在不了解Nova接管关系的情况下，手工修改由Nova维护的VCPU、内存和本地磁盘清单，否则下一次资源更新可能覆盖人工内容，或者造成Nova记录与Placement记录不一致。资源由哪个服务拥有，应在平台设计中明确。

四. Trait资源特征

Trait用于描述资源提供者具有的定性能力，例如处理器指令集、存储介质类型、硬件架构、可信计算能力或虚拟化特性。Trait本身没有可分配数量，不能像VCPU那样被消耗。调度请求可以要求必须具备某些Trait，或排除具有某些Trait的提供者。

标准Trait由OpenStack生态统一定义，便于不同服务使用共同名称。需要表达平台特有能力时，可以使用CUSTOM_前缀的自定义Trait。自定义Trait应来自真实、稳定的能力，不能把临时标签当作永久硬件特征。若镜像要求特定CPU能力，Nova可以把镜像属性转换为资源请求，再由Placement筛选具有对应Trait的提供者。

Trait与Resource Class经常一起出现，但二者解决的问题不同。资源类别回答“需要哪种可计量资源”，特征回答“提供者必须具备什么性质”。一个GPU既可能通过资源类别表达可分配数量，也可能通过Trait表达型号或功能。只有把数量和能力同时建模，调度结果才能满足工作负载的完整要求。

## 8.2 Allocation、Consumer与调度协作

一. Allocation资源分配

Allocation记录某个Consumer从某个Resource Provider占用了某类资源的数量。它把消费者、资源提供者、资源类别和数量连接起来。若一台实例从compute取得2个VCPU和4096 MiB内存，Placement会形成相应分配记录；若请求还需要共享存储或加速设备，一个消费者可以同时在多个提供者上具有分配。

Allocation不是操作系统实际使用率。虚拟机当前可能没有把所分配的CPU时间或内存全部用完，但这些资源已经按调度承诺保留给该消费者。Placement关注的是资源承诺与可分配容量，监控系统关注的是实时利用率，两类数据不能互相替代。

分配随着资源生命周期变化。实例创建时建立资源承诺，调整实例规格可能改变分配，迁移过程可能暂时涉及源和目标提供者，实例删除后应释放相应分配。Nova负责在业务流程中维护这些关系，Placement负责保存和提供一致的资源视图。

二. Consumer消费者

Consumer表示占用资源的对象。Nova实例是最常见的消费者，迁移过程等也可能具有独立消费者标识。Consumer通常由UUID识别，并可以关联项目与用户信息。通过Consumer，Placement能够回答某项资源被谁占用，而不只是记录一个无法追溯的总使用量。

Consumer与Keystone用户不是同一对象。Keystone用户表示身份，Placement Consumer表示资源占用主体。实例归属于某个项目和用户，但实例自身的UUID可以作为消费者标识。区分身份对象、资源对象和占用对象，有助于理解跨服务数据之间为什么需要明确ID关系。

Consumer也具有Generation，用于保护并发更新。一个资源申请可能同时影响多个提供者和多种资源，更新时必须以一致方式处理消费者和提供者Generation。生产平台中的资源数据直接影响调度公平、容量规划和用户体验，对数量、标识和并发关系的严谨维护体现了工程人员对平台公共资源负责的职业意识。

三. Allocation Candidate分配候选

Allocation Candidate是Placement根据资源请求返回的可行资源组合。请求可以包含资源类别与数量、必需或禁止的Trait、Aggregate关系以及更复杂的提供者拓扑要求。返回结果通常包括满足请求的分配方案和相关提供者摘要，使Nova Scheduler能够继续完成过滤、称重和最终选择。

候选结果表示“在当前资源记录下可以满足”，不是已经完成资源占用。资源状态可能在候选生成后继续变化，因此Nova还要在后续流程中建立Allocation并处理并发冲突。只有分配写入成功，资源承诺才进入Placement的已用数量。

Placement不会根据用户偏好、故障域策略或所有Nova配置直接替Scheduler作出唯一选择。它提供结构化候选，Scheduler结合Compute Filter、Weigher、Host Aggregate等规则决定目标。把候选生成与最终决策分开，使资源模型可以保持通用，也使Nova保留计算调度策略。

四. Placement与Nova的协作顺序

在计算节点加入云平台后，nova-compute资源跟踪器建立与主机对应的Resource Provider，写入VCPU、MEMORY_MB、DISK_GB等Inventory，并根据硬件和虚拟化能力设置Trait。后续资源变化会继续更新Placement，使控制面取得较新的供给信息。

用户提交创建实例请求时，Nova API取得规格、镜像、网络等条件，Scheduler把其中可由Placement表达的需求组织为资源请求。Placement返回Allocation Candidate，Scheduler继续筛选和排序。目标确定后，Nova为消费者建立Allocation，再把创建任务交给目标compute上的服务进程。

若没有Placement，Nova无法在当前架构下取得统一资源清单和分配候选；若Placement数据不准确，Scheduler也会基于错误事实进行选择。因此，本章必须在第九章Nova之前完成。数据库、身份、API和Apache承载准备好以后，下一章的nova-compute才能把计算资源登记到Placement。

五. Placement的服务承载

Placement把持久化对象保存在独立的placement数据库中，把API通过Apache和WSGI承载在controller的8778端口。Keystone中的placement用户用于API服务认证，服务目录中的placement类型和三个Endpoint用于客户端发现地址。Memcached由认证中间件使用，RabbitMQ不是Placement本章配置文件中的直接通信入口。

本地Antelope软件包提供/etc/placement/placement.conf、Apache配置和默认策略文件。placement.conf中的[placement_database]连接数据库，[api]选择keystone认证策略，[keystone_authtoken]写入服务身份和缓存地址，[oslo_policy]指定策略文件。各配置段分别对应持久化、认证和授权，不应把所有参数集中到[DEFAULT]段。

本实验的软件包仍附带空映射形式的policy.json。OpenStack服务的策略文件已经转向YAML格式，因此本章使用oslopolicy-convert-json-to-yaml把软件包默认JSON等价转换为policy.yaml，并在placement.conf中明确指定policy_file = policy.yaml。空映射表示没有增加自定义覆盖，服务继续使用代码中的默认策略，并不表示Placement没有访问控制。

Apache的00-placement-api.conf只保留8778虚拟主机中的WSGI入口。Listen指令使Apache接收8778端口连接，WSGIDaemonProcess指定Placement进程组、线程和运行用户，WSGIScriptAlias把根路径交给/usr/bin/placement-api，WSGIPassAuthorization On允许认证信息传递给WSGI应用。Placement没有单独需要启动的placement.service，本实验通过重新启动httpd加载API。

## 8.3 实训项目5 Placement的手工安装与配置

一．实训前提环境：

已经完成实训项目4的全部内容。controller上的MariaDB、Memcached、Apache、Keystone和Glance已经完成配置，/root/admin-openrc与service项目可以继续使用，openstack-local教学仓已经准备。本实训从第七章结束后的教学快照继续进行。

本章继续使用qwer1234作为Placement数据库账户和Keystone服务用户的课堂口令。该口令只允许出现在可重置的隔离教学环境。placement.conf含有明文服务口令，应限制文件读取权限，不能把配置内容连同真实生产凭据发布到教材附件或公共仓库。

二．实训涉及节点：

Placement数据库、Keystone对象、服务程序、策略文件、数据库同步和Apache承载全部在controller完成。下一章安装Nova时，compute上的nova-compute将向Placement登记计算资源，形成控制节点与计算节点之间的资源数据联系。

三．实训目标：

理解Resource Provider、Resource Class、Inventory、Trait、Allocation、Consumer和Allocation Candidate之间的关系；创建placement数据库及三种来源的数据库用户并授权；创建placement服务用户和admin角色授权；登记placement服务及RegionOne中的三个端点；安装openstack-placement-api；使用vi编辑placement.conf；把本地软件包的默认policy.json等价转换为policy.yaml；同步Placement数据库；使用vi配置Apache的8778虚拟主机；启用并重新启动httpd。

四．实训步骤及其详解：

步骤一：创建Placement数据库及数据库用户

Placement需要独立数据库保存资源提供者、清单、特征、消费者和分配关系。首先在controller使用MariaDB root账户进入数据库客户端。

```command
[root@controller ~]# mysql -uroot -pqwer1234
```

创建名为placement的数据库。

```command
MariaDB [(none)]> CREATE DATABASE placement;
```

分别创建允许从localhost、127.0.0.1和其他管理网络地址连接的placement数据库账户。

```command
MariaDB [(none)]> CREATE USER 'placement'@'localhost' IDENTIFIED BY 'qwer1234';
MariaDB [(none)]> CREATE USER 'placement'@'127.0.0.1' IDENTIFIED BY 'qwer1234';
MariaDB [(none)]> CREATE USER 'placement'@'%' IDENTIFIED BY 'qwer1234';
```

把placement数据库中的全部权限授予三个账户。SQL语句换行后，MariaDB使用->提示继续输入。

```command
MariaDB [(none)]> GRANT ALL PRIVILEGES ON placement.*
    -> TO 'placement'@'localhost';
MariaDB [(none)]> GRANT ALL PRIVILEGES ON placement.*
    -> TO 'placement'@'127.0.0.1';
MariaDB [(none)]> GRANT ALL PRIVILEGES ON placement.*
    -> TO 'placement'@'%';
```

重新载入权限表并退出数据库客户端。

```command
MariaDB [(none)]> FLUSH PRIVILEGES;
MariaDB [(none)]> EXIT;
```

placement数据库用户只取得placement数据库的权限，不使用MariaDB root账户运行服务。三种连接来源与前两章保持一致，便于组件通过本地主机名、本地TCP或受控管理网络建立连接。

步骤二：创建Placement服务用户及角色授权

加载管理员环境变量，进入可以创建Keystone对象的Shell上下文。

```command
[root@controller ~]# . /root/admin-openrc
```

在Default域中创建placement用户。

```command
[root@controller ~]# openstack user create --domain default --password qwer1234 placement
```

把admin角色授予placement用户在service项目中的身份。

```command
[root@controller ~]# openstack role add --project service --user placement admin
```

这里创建的是Keystone服务身份。Linux中的placement系统用户由软件包提供，MariaDB中的placement账户已经在步骤一建立，三者不能互相替代。

步骤三：创建Placement服务和三类端点

在Keystone服务目录中创建名称和类型都为placement的服务条目。

```command
[root@controller ~]# openstack service create --name placement --description "Placement API" placement
```

在RegionOne中依次创建public、internal和admin端点，三类URL都指向controller的8778端口。

```command
[root@controller ~]# openstack endpoint create --region RegionOne placement public http://controller:8778
[root@controller ~]# openstack endpoint create --region RegionOne placement internal http://controller:8778
[root@controller ~]# openstack endpoint create --region RegionOne placement admin http://controller:8778
```

placement是服务类型，http://controller:8778是本实验的API地址。三类接口在教学拓扑中共用同一URL，但客户端仍会根据接口语义和RegionOne选择端点。

步骤四：安装Placement软件包

从openstack-local教学仓安装Antelope版本的Placement API软件包。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo='openstack-local' install openstack-placement-api
```

软件包提供Placement API、管理命令、placement系统用户、默认配置文件、策略文件以及Apache WSGI配置。本章不在compute安装Placement软件包。

步骤五：手工编辑Placement主配置文件

使用vi打开/etc/placement/placement.conf，配置数据库、Keystone认证和YAML策略文件。

```command
[root@controller ~]# vi /etc/placement/placement.conf
```

在文件中写入或修改以下配置段。同名段中若存在其他生效值，应在vi中注释旧值，只保留本实验配置。

```config
[placement_database]
connection = mysql+pymysql://placement:qwer1234@127.0.0.1/placement

[api]
auth_strategy = keystone

[keystone_authtoken]
www_authenticate_uri = http://controller:5000
auth_url = http://controller:5000/v3
memcached_servers = controller:11211
auth_type = password
project_domain_name = Default
user_domain_name = Default
project_name = service
username = placement
password = qwer1234

[oslo_policy]
policy_file = policy.yaml
```

[placement_database]段中的两个placement分别表示数据库用户和数据库名称，127.0.0.1表示MariaDB位于同一controller。[api]段要求API采用Keystone认证，[keystone_authtoken]段给出服务身份、认证地址和缓存地址。[oslo_policy]段使Placement读取随后生成的policy.yaml。

保存文件后设置属组与权限，使Placement服务可以读取配置，普通用户不能读取其中的课堂口令。

```command
[root@controller ~]# chown root:placement /etc/placement/placement.conf
[root@controller ~]# chmod 640 /etc/placement/placement.conf
```

步骤六：把默认策略文件转换为YAML格式

本地Antelope软件包提供/etc/placement/policy.json，其内容为空映射，没有自定义策略覆盖。先保留软件包默认文件副本，再使用发行包提供的转换工具生成policy.yaml。

```command
[root@controller ~]# cp -a /etc/placement/policy.json /etc/placement/policy.json.bak
[root@controller ~]# oslopolicy-convert-json-to-yaml --namespace placement --policy-file /etc/placement/policy.json --output-file /etc/placement/policy.yaml
```

转换只是把JSON空映射等价迁移到YAML表示，不增加新的角色权限。按照placement.conf中的policy_file设置，服务将读取/etc/placement/policy.yaml。为该文件设置与主配置一致的属组和读取权限。

```command
[root@controller ~]# chown root:placement /etc/placement/policy.yaml
[root@controller ~]# chmod 640 /etc/placement/policy.yaml
```

生产环境若需要调整策略，应从职责分离和最小权限出发逐项设计，不能因为教学文件为空就误认为可以任意放宽接口访问。

步骤七：同步Placement数据库

配置文件和策略文件准备完成后，以placement系统用户身份执行数据库同步。

```command
[root@controller ~]# su -s /bin/sh -c "placement-manage db sync" placement
```

该操作把Antelope版本需要的资源提供者、资源类别、清单、特征、消费者、分配和迁移版本等数据结构写入placement数据库。同步完成后继续配置Apache，使这些数据结构能够在Nova接入时通过Placement API得到使用。

步骤八：手工配置Apache的Placement WSGI入口

使用vi打开/etc/httpd/conf.d/00-placement-api.conf。本实验只保留8778虚拟主机中的根WSGI入口，使Placement API在独立端口承载。

```command
[root@controller ~]# vi /etc/httpd/conf.d/00-placement-api.conf
```

把文件内容整理为以下配置。

```config
Listen 8778

<VirtualHost *:8778>
  WSGIProcessGroup placement-api
  WSGIApplicationGroup %{GLOBAL}
  WSGIPassAuthorization On
  WSGIDaemonProcess placement-api processes=3 threads=1 user=placement group=placement
  WSGIScriptAlias / /usr/bin/placement-api
  <IfVersion >= 2.4>
    ErrorLogFormat "%M"
  </IfVersion>
  ErrorLog /var/log/placement/placement-api.log
  <Directory /usr/bin>
    <IfVersion >= 2.4>
      Require all granted
    </IfVersion>
    <IfVersion < 2.4>
      Order allow,deny
      Allow from all
    </IfVersion>
  </Directory>
</VirtualHost>
```

Listen 8778与第三步创建的Endpoint端口保持一致。WSGIDaemonProcess让API以placement用户和组运行，WSGIPassAuthorization On把认证信息交给应用，WSGIScriptAlias把虚拟主机根路径映射到Placement API入口。Directory段允许Apache访问WSGI程序，接口上的业务请求仍由Keystone认证和Placement策略控制。

保存后把Apache配置文件设置为root所有，并限制普通用户修改或读取不必要的服务细节。

```command
[root@controller ~]# chown root:root /etc/httpd/conf.d/00-placement-api.conf
[root@controller ~]# chmod 640 /etc/httpd/conf.d/00-placement-api.conf
```

步骤九：启用并重新启动Apache服务

Keystone已经使用httpd承载Identity API，本章继续把httpd加入开机启动，并通过重新启动加载Placement的8778虚拟主机和WSGI应用。

```command
[root@controller ~]# systemctl enable httpd.service
[root@controller ~]# systemctl restart httpd.service
```

Placement API由httpd通过WSGI承载，因此服务启停落在Apache而不是独立的placement.service上。httpd重新启动后会同时承载既有Keystone入口和新增Placement入口。下一章将在这一基础上先安装Nova控制节点服务，再安装compute上的计算服务，并由Nova把真实计算资源接入Placement，使本章讲解的资源提供者、清单、特征、消费者和分配关系进入实际调度流程。
