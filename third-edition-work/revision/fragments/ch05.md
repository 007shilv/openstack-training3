# 第五章 MariaDB数据库及基础服务的安装与配置

本章导读：本章介绍MariaDB数据库以及OpenStack控制面所依赖的基础服务。数据库是云平台保存持久化元数据的场所，消息队列承担不同服务进程之间的通信，缓存服务提高频繁访问数据的处理效率，统一命令行客户端则为后续创建身份对象和管理云资源提供共同入口。这些服务虽然不直接创建虚拟机，却共同构成OpenStack各组件可以协同工作的基础。

我们先从关系型数据库的基本概念出发，再认识MariaDB、RabbitMQ、Memcached和OpenStackClient在控制面中的作用，最后在openEuler 24.03 LTS SP3上逐项完成安装与配置。学习时既要看到每一项服务的独立作用，也要理解它们之间的先后关系：先准备持久化数据服务，再建立消息通信和缓存能力，最后安装统一客户端，为第六章的身份服务部署做好准备。

本书实验环境中的示例口令统一写为qwer1234。该环境与生产网络隔离，不保存真实业务数据；生产环境需要为数据库管理员、数据库服务用户、消息队列用户和OpenStack服务用户分别设置高强度口令，并配合访问控制、加密传输和凭据管理机制。

## 5.1 MariaDB数据库功能简介

一．关系型数据库的基本结构

1．数据库、表与记录

MariaDB是一种开源关系型数据库管理系统，与MySQL具有共同的技术渊源，并保持了较好的协议和使用习惯兼容性。openEuler软件仓提供MariaDB软件包，本书使用它为OpenStack控制面保存结构化数据。后续安装Keystone、Glance、Placement、Nova、Neutron和Cinder时，每个组件都会建立自己的数据库和数据库账户，再把数据库连接地址写入组件配置文件。

数据库（Database）是按照一定的数据结构组织、保存和管理数据的集合。若把所有内容都直接写入普通文件，不同服务进程很难同时完成一致的查询和修改，也难以表达对象之间的关联关系。关系型数据库管理系统把数据组织成相互关联的表，并通过事务、约束和索引等机制，为并发访问提供稳定的数据管理能力。

关系型数据库中的表可以理解为结构明确的数据集合。每一行代表一条记录，每一列代表一种属性。例如，身份服务可以用不同的表保存用户、项目和角色，并通过标识符建立这些对象之间的联系。数据库模式规定表的结构，数据记录则是在该结构下保存的具体内容。理解“数据库—表—行—列”的层次，是阅读后续组件数据库配置的基础。

主键用于唯一标识一条记录。一个表中的不同记录不能具有相同的主键值，因此组件可以利用主键准确找到某个对象。外键用于表达表与表之间的引用关系，使数据库能够约束相关对象的连接。索引则像教材的目录，可以帮助数据库较快地定位满足条件的记录。索引能够提高查询效率，但也会增加写入和维护成本，所以它通常由OpenStack组件的数据库迁移过程统一建立，而不是由学习者自行增删。

2．事务、存储引擎与字符集

事务把一组相关的数据操作视为一个整体。当一次云平台操作需要同时修改多张表时，事务可以使这些修改全部完成，或者在发生问题时全部不生效，从而减少只完成一半所造成的数据矛盾。InnoDB支持事务和行级并发控制，因此本书把它设置为MariaDB的默认存储引擎。后续各组件同步数据库时，组件自身携带的迁移内容会建立所需的数据表、索引和约束。

字符集决定字符怎样编码，排序规则决定字符怎样比较和排列。本实验把服务端字符集设置为utf8，把排序规则设置为utf8_general_ci，使不同OpenStack组件连接数据库时使用一致的字符处理方式。生产系统还要结合数据范围、排序要求和迁移方案选择合适的字符集与排序规则。

二．MariaDB在OpenStack中的作用

1．控制面元数据的持久化

连接数表示数据库可以同时接受的连接数量。OpenStack控制面包含多个API、调度和后台服务进程，这些进程会分别建立数据库连接。若连接上限过小，多个组件并发运行时可能无法取得数据库连接。本实验把max_connections设置为4096，为双节点环境预留控制面连接空间。生产环境还应根据控制节点数量、服务进程数、连接池配置和数据库承载能力进行计算。

MariaDB在本平台中保存的是控制面元数据，而不是所有云资源的实际内容。Keystone数据库保存身份对象与授权关系，Glance数据库保存镜像记录，Nova数据库保存计算资源和实例记录，Neutron数据库保存网络对象，Cinder数据库保存卷的控制信息。镜像文件、虚拟机磁盘和对象数据分别由对应的存储后端承担，不能把数据库理解为整个云平台的数据仓库。

图5.1表示OpenStack控制面数据库与各组件数据的关系。MariaDB保存身份、镜像、计算、网络和卷的元数据，各组件通过独立数据库账户访问自己的数据库；镜像文件、实例磁盘、块数据和对象数据仍保存在相应后端。

2．组件数据库与账户边界

为了让不同组件的数据边界清晰，本书为每个OpenStack组件分别建立数据库和数据库用户。例如，第六章将建立keystone数据库与keystone数据库用户，后续章节还会按照同样思路建立glance、placement、nova、neutron和cinder等数据库。组件只取得自己数据库所需的权限，这种分离有利于减少误操作影响范围，也便于定位配置归属。

MariaDB客户端使用不同的提示符表示当前上下文。尚未选择数据库时显示MariaDB [(none)]>，选择某个数据库后会显示包含数据库名称的提示符；一条SQL语句尚未以分号结束时，客户端使用->提示继续输入。提示符不是SQL语句的一部分，却能帮助读者判断命令正在Linux终端还是数据库客户端中执行。第六章创建Keystone数据库时，将按照这些真实提示符逐条输入SQL语句。

SQL可以完成数据定义、数据处理和权限控制等工作。CREATE DATABASE用于建立数据库，CREATE USER用于建立数据库账户，GRANT用于授予指定数据库的访问权限。后续组件部署将反复使用建库、建用户和授权操作，这三类语句正好把数据库基本知识与信创云平台的真实依赖连接起来。

数据库账户与Linux账户具有不同的身份空间。MariaDB根据用户名和连接来源共同识别账户，'keystone'@'localhost'、'keystone'@'127.0.0.1'和'keystone'@'%'可以使用相同用户名，却是三条不同的数据库账户记录。localhost适合通过本地主机名称建立连接，127.0.0.1对应本地TCP连接，%用于匹配其他允许来源。后续建库时分别创建这些账户，是为了让连接方式与授权关系保持清晰，而不是让所有OpenStack组件共同使用数据库root。

每个组件配置文件中的数据库连接串都包含协议驱动、数据库用户、口令、数据库主机和数据库名称。用户名或数据库名写错会把服务指向错误的数据边界，主机写错会改变连接位置，口令中的URL保留字符还需要采用适当编码。实验口令qwer1234不含URL保留字符。

OpenStack服务通常通过连接池复用数据库连接，而不是每处理一次请求都永久占用一条新连接。连接池可以减少反复建立连接的开销，但多个服务进程的连接数量会叠加。因此，数据库连接上限、组件工作进程数和控制节点内存应当统筹规划。

## 5.2 OpenStack基础服务功能简介

OpenStack采用分布式服务架构。一个用户请求进入API服务后，可能还要经过身份认证、任务调度、消息传递、数据库读写以及计算或网络节点上的后台进程。不同进程不适合通过彼此直接调用和等待来完成所有协作，因此控制面除数据库之外，还需要消息队列、缓存和统一客户端等基础能力。

图5.2表示控制面基础服务的协作关系。OpenStack API和后台进程把需要持久保存的状态写入MariaDB，通过RabbitMQ交换任务，通过Memcached使用短期缓存；OpenStack统一客户端位于访问侧，向各组件API发送命令请求。

{{FIGURE:图5.2}}

图5.2中的四类基础能力不能相互替代。数据库保存持久状态，消息队列传递异步任务，缓存减少重复访问，客户端提供统一操作入口。后续组件必须按照数据库、消息、缓存和客户端已经可用的前提进行安装。

一．RabbitMQ消息队列

1．生产者、队列与消费者

RabbitMQ是本实验环境使用的消息队列服务。OpenStack中的API进程、调度进程和节点代理常通过消息队列传递远程过程调用请求、操作指令和运行信息。例如，计算服务接收创建实例请求后，控制节点上的不同Nova进程需要交换任务信息，最终把工作交给计算节点上的服务进程。消息队列把发送方和接收方解耦，使它们不必在同一时刻以一条直接连接完成全部处理。

消息队列中的生产者负责发送消息，消费者负责取得并处理消息，交换器根据路由关系把消息送往相应队列。OpenStack服务通过公共通信库使用这些机制，学习者通常不需要手工创建每一个业务交换器和队列，但必须为服务准备能够访问RabbitMQ的账户，并在各组件配置文件的transport_url参数中使用同一账户信息。

本书在RabbitMQ中创建名为openstack的账户，并为它授予默认虚拟主机/上的配置、写入和读取权限。这里的openstack是RabbitMQ账户，不是Linux用户，也不是Keystone身份用户。相同名称出现在不同系统中时，必须根据命令提示符和配置位置判断它属于哪一种对象。

RabbitMQ传递的是服务间消息，不负责决定资源应该调度到哪台主机，也不替代组件数据库。Nova Scheduler仍负责计算资源选择，数据库仍保存需要持久化的控制信息。消息队列的职责是让这些服务可靠地交换任务和结果。把消息通信、业务决策与持久化存储分开理解，有助于后续阅读Nova、Neutron和Cinder的配置。

二．Memcached缓存服务

1．缓存与持久化数据的区别

Memcached是一种内存缓存服务，它用内存保存短期、可重新取得的数据，以减少重复计算和频繁访问后端服务的开销。身份认证过程中会反复处理与认证有关的信息，适当使用缓存可以缩短访问路径。缓存中的内容不是云平台唯一的数据副本，服务重启后可以根据后端数据重新生成，因此不能把Memcached当作数据库或长期存储。

Memcached通过监听地址决定哪些网络接口可以接受连接。本实验让它监听127.0.0.1、::1和controller的管理地址192.168.234.151，使控制节点本地服务以及管理网络中的OpenStack服务能够访问缓存。生产环境还应进一步限制来源地址，并在网络边界上只开放必要的访问路径。

2．监听与内存参数

PORT指定Memcached使用的服务端口，USER指定运行服务的系统用户，MAXCONN限制可同时接受的连接数量，CACHESIZE决定用于缓存的内存容量，OPTIONS用于补充监听地址等启动参数。这些参数共同定义缓存服务怎样使用系统资源。设置过大可能挤占控制节点内存，设置过小又会削弱缓存效果，因此实际项目应结合用户规模、认证请求量和控制节点资源进行调整。

Fernet令牌、Credential密钥和Memcached缓存是三种不同机制。Fernet密钥用于保护Keystone签发的令牌，Credential密钥用于保护Keystone保存的凭据数据，Memcached则提供运行时缓存。缓存不能替代密钥仓，密钥仓也不能替代数据库。第六章会分别初始化Fernet与Credential密钥仓，读者应保持这些概念的边界。

三．OpenStack统一命令行客户端

1．统一命令入口

OpenStackClient提供统一的openstack命令入口。早期OpenStack各项目曾分别提供不同命令行工具，命令风格和参数并不完全一致。统一客户端把身份、镜像、计算、网络和块存储等常用操作组织在同一命令结构下，便于学习者在一个终端环境中管理不同服务对象。

客户端本身不是运行在云平台控制面的服务端组件，也不承担认证或资源调度。它读取管理员环境变量，向服务端API发送请求，再显示返回结果。第六章将使用它创建service项目，后续章节还会使用它创建服务用户、角色授权、服务条目和三类端点。本章先把客户端准备好，下一章再开始身份对象操作。

四．时间基础与服务依赖

1．时间一致性

分布式云平台需要一致的时间基准。令牌有效期、消息处理、日志顺序和任务调度都依赖节点时间。第四章已经在controller和compute上安装并启动chronyd，本章沿用该时间基础，不重复改变上游时间源。环境基础先于组件服务准备，也避免在每个组件章节反复配置同一项系统服务。

MariaDB、RabbitMQ和Memcached在职责上彼此独立，在部署顺序上存在清晰关系。数据库先提供持久化基础，消息队列再提供服务通信通道，缓存服务补充高频数据访问能力，统一客户端最后为身份对象和资源管理提供操作入口。

## 5.3 实训项目2 MariaDB数据库及基础服务的手工安装与配置

一．实训前提环境

已经完成实训项目1的全部内容，controller和compute运行openEuler 24.03 LTS SP3，主机名与管理地址已经固定，/etc/hosts能够解析两个节点，openstack-local软件仓已经配置，chronyd已经启动。

本实训使用qwer1234作为统一实验口令。

二．实训涉及节点

本实训只在controller节点安装MariaDB、RabbitMQ、Memcached和OpenStackClient。compute暂不安装这些控制面基础服务。每次输入命令前先根据[root@controller ~]#提示符辨认当前节点。

三．实训目标

1．完成MariaDB软件包安装、配置文件编辑和服务启动。

2．完成MariaDB管理员口令和基础安全设置。

3．完成RabbitMQ安装、openstack账户创建和权限设置。

4．完成Memcached安装、监听地址配置和服务启动。

5．完成OpenStack统一命令行客户端安装。

四．实训步骤及其详解

步骤一：安装MariaDB基本组件

首先在controller安装MariaDB服务器、客户端配置和OpenStack访问数据库所需的驱动软件包。命令只启用第四章准备的openstack-local软件仓。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo='openstack-local' install mariadb-config mariadb mariadb-server python3-PyMySQL
```

mariadb-server提供数据库服务进程，mariadb提供客户端工具，mariadb-config提供公共配置内容，python3-PyMySQL是OpenStack组件连接MariaDB所需的发行版运行时驱动包。软件包名称中的python3是RPM命名的一部分，本章不展开编程内容。

步骤二：手工编辑MariaDB的OpenStack配置

软件包安装完成后，使用vi创建/etc/my.cnf.d/openstack.cnf。该文件把OpenStack实验所需参数集中在[mysqld]段中，便于与系统默认配置分开管理。

```command
[root@controller ~]# vi /etc/my.cnf.d/openstack.cnf
```

进入vi后写入以下内容，配置文件正文不带Shell提示符。

```config
[mysqld]
bind-address = 0.0.0.0
default-storage-engine = innodb
innodb_file_per_table = on
max_connections = 4096
collation-server = utf8_general_ci
character-set-server = utf8
```

bind-address = 0.0.0.0使MariaDB在本实验节点的网络地址上提供服务，方便后续组件通过管理网络连接。生产环境通常绑定受控管理地址，并结合防火墙和访问来源缩小暴露范围。

default-storage-engine选择InnoDB作为默认存储引擎，innodb_file_per_table使InnoDB表使用独立表空间。max_connections提高控制面可用连接上限，字符集和排序规则使各组件使用一致的文本处理方式。保存文件时应逐项核对参数名、等号和数值，避免因拼写差异产生后续连接问题。

步骤三：启用并启动MariaDB服务

配置文件保存后，先把MariaDB加入开机启动，再启动当前服务。两条命令分开输入，可以使学习者明确“下次开机自动启动”和“本次立即启动”是两个不同动作。

```command
[root@controller ~]# systemctl enable mariadb.service
[root@controller ~]# systemctl start mariadb.service
```

MariaDB首次启动后，使用发行版提供的交互工具完成基础安全设置。

```command
[root@controller ~]# mysql_secure_installation
```

程序首先要求输入当前root密码。首次安装尚未设置密码时直接按Enter键，然后选择设置root密码，并连续两次输入qwer1234。随后删除匿名用户，禁止root从远程主机登录，删除test数据库并重新载入权限表。数据库root仍可在controller本机完成后续建库工作，OpenStack组件则使用各自独立的数据库账户连接。

数据库root用于本机完成后续建库工作，OpenStack组件使用各自独立的数据库账户连接。

步骤四：安装并启动RabbitMQ

MariaDB完成后，继续在controller安装RabbitMQ服务。消息队列必须先运行，后续OpenStack组件才能使用transport_url建立RPC通信。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo='openstack-local' install rabbitmq-server
```

软件包安装完成后，先设置开机启动，再启动当前RabbitMQ服务。

```command
[root@controller ~]# systemctl enable rabbitmq-server.service
[root@controller ~]# systemctl start rabbitmq-server.service
```

接着创建名为openstack的RabbitMQ账户，口令使用本书统一的qwer1234。

```command
[root@controller ~]# rabbitmqctl add_user openstack qwer1234
```

账户建立后，为它授予默认虚拟主机/上的配置、写入和读取权限。三个".*"依次对应configure、write和read权限范围，表示允许OpenStack服务使用所需的消息对象。

```command
[root@controller ~]# rabbitmqctl set_permissions -p / openstack ".*" ".*" ".*"
```

后续组件配置中的transport_url将写为rabbit://openstack:qwer1234@controller:5672/一类连接地址。该地址把消息队列账户、口令、主机和服务入口组合在一起，必须与本步骤创建的账户保持一致。

步骤五：安装并配置Memcached

消息队列完成后，安装Memcached服务及OpenStack访问缓存所需的运行时驱动包。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo='openstack-local' install memcached python3-memcached
```

使用vi打开/etc/sysconfig/memcached，保留变量结构并把内容整理为本实验所需的监听地址与资源参数。

```command
[root@controller ~]# vi /etc/sysconfig/memcached
```

在文件中写入以下内容。

```config
PORT="11211"
USER="memcached"
MAXCONN="1024"
CACHESIZE="64"
OPTIONS="-l 127.0.0.1,::1,192.168.234.151"
```

127.0.0.1和::1供controller本机进程访问，192.168.234.151是controller管理地址，供管理网络中的OpenStack服务连接。MAXCONN和CACHESIZE分别限制连接数量与缓存容量。

配置保存后，启用并启动Memcached服务。

```command
[root@controller ~]# systemctl enable memcached.service
[root@controller ~]# systemctl start memcached.service
```

步骤六：安装OpenStack统一命令行客户端

基础服务完成后，在controller安装OpenStackClient。该软件包提供后续章节使用的openstack命令，但它不需要作为系统服务启动。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo='openstack-local' install python3-openstackclient
```

完成上述步骤后，controller已经具备OpenStack控制面所需的数据库、消息队列、缓存和统一客户端基础。下一章将在这些依赖之上手工安装和配置Keystone身份服务，并开始建立云平台的身份与服务目录。
