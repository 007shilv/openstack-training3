# 第十四章 OpenStack云平台各组件运维

本章导读：OpenStack云平台投入使用后，日常工作围绕身份、镜像、资源清单、实例、网络、块存储、对象存储和图形界面展开。不同组件保存不同类型的事实：Keystone确定“谁可以在什么范围内做什么”，Glance保存镜像及其属性，Placement记录资源供给与分配，Nova维护实例生命周期，Neutron组织网络连接，Cinder提供持久块设备，Swift保存对象数据，Horizon把这些API组织成浏览器页面。运维人员需要沿对象之间的引用关系操作，而不能只依据界面中的名称判断资源归属。

本章在独立项目bookops中完成操作。项目用户为bookops-user，用户组为bookops-group，资源名称统一使用bookops-前缀。独立项目既能展示组件间的真实协作，又能把新增资源与平台原有资源分开。表14-1列出本章使用的身份对象。

## 14.1 Keystone身份与权限运维

一．运维目标

1．理解域、项目、用户、用户组、角色和角色授权之间的关系。

2．创建独立项目与普通用户，通过用户组完成项目范围授权。

3．查看服务和端点，能够沿服务目录定位组件API。

4．建立普通用户环境变量文件，区分管理员操作与项目用户操作。

二．身份对象与授权关系

1．域、项目和用户

Keystone Identity Service（Keystone身份认证服务）把身份对象和资源范围分开管理。域是项目、用户和用户组的上级命名空间；项目是计算、网络和存储资源的主要隔离边界；用户表示可以认证的主体。用户名便于人识别，服务之间实际使用对象标识建立关联。

用户成功认证并不等于可以操作项目资源。Keystone还要检查用户是否在目标项目上获得角色。角色本身只是一个权限名称，角色授权把“角色—用户或用户组—项目”连接起来。使用用户组集中授权，可以在人员变化时只调整组成员，而不必反复修改每个项目的角色关系。

2．服务、端点和区域

服务对象记录组件的服务类型，例如identity、image、compute、network、volumev3、object-store和placement。端点把服务类型映射到具体URL，并按Region、public、internal和admin接口分类。客户端先向Keystone取得作用域令牌和服务目录，再根据服务类型、区域和接口选择目标API。

RegionOne表示本书环境使用的区域名称。public接口通常面向云用户，internal接口用于云内服务协作，admin接口供管理网络使用。三个接口可以使用相同地址，也可以部署在不同网络。端点存在不代表后端服务一定可达，因此身份目录检查与服务状态检查需要结合进行。

三．创建身份运维沙箱

1．载入管理员环境

在controller载入管理员环境变量，查看Default域和现有角色。管理员环境只用于创建项目、用户、用户组和角色授权。

```command
[root@controller ~]# source /root/admin-openrc
[root@controller ~]# openstack domain show Default
[root@controller ~]# openstack role list
```

2．创建项目、用户和用户组

创建bookops项目和bookops-user用户，用户口令按本书实验环境统一设置为qwer1234。随后建立bookops-group，并把用户加入用户组。

```command
[root@controller ~]# openstack project create --domain Default --description "OpenStack组件运维" bookops
[root@controller ~]# openstack user create --domain Default --project bookops --password qwer1234 bookops-user
[root@controller ~]# openstack group create --domain Default --description "组件运维用户组" bookops-group
[root@controller ~]# openstack group add user bookops-group bookops-user
```

3．授予项目角色

把member角色授予bookops项目中的bookops-group。Swift代理配置允许admin和user角色访问对象存储；若平台尚无user角色，先创建该角色，再授予同一用户组。角色名称区分大小写，授权范围是bookops项目，不是整个云平台。

```command
[root@controller ~]# openstack role add --project bookops --group bookops-group member
[root@controller ~]# openstack role create user
[root@controller ~]# openstack role add --project bookops --group bookops-group user
```

4．建立普通用户环境变量文件

使用vi建立/root/bookops-openrc。该文件只保存本书实验用户的连接参数，权限设置为仅root可读写。

```command
[root@controller ~]# vi /root/bookops-openrc
```

```config
export OS_PROJECT_DOMAIN_NAME=Default
export OS_USER_DOMAIN_NAME=Default
export OS_PROJECT_NAME=bookops
export OS_USERNAME=bookops-user
export OS_PASSWORD=qwer1234
export OS_AUTH_URL=http://controller:5000/v3
export OS_IDENTITY_API_VERSION=3
export OS_IMAGE_API_VERSION=2
export OS_REGION_NAME=RegionOne
```

```command
[root@controller ~]# chmod 600 /root/bookops-openrc
[root@controller ~]# source /root/bookops-openrc
[root@controller ~]# openstack token issue
```

令牌命令返回用户、项目、过期时间和令牌标识。令牌属于认证凭据，不应复制到书稿、工单或公共日志中；确认认证成功后只记录用户和项目范围。

五．身份对象的日常调整

1．禁用与启用用户

临时停止某个普通用户登录时，可以禁用用户，再在处理完成后启用。操作前应确认对象名称和域，避免命中其他域中的同名用户。

```command
[root@controller ~]# openstack user set --disable bookops-user
[root@controller ~]# openstack user show bookops-user -c name -c enabled
[root@controller ~]# openstack user set --enable bookops-user
```

2．调整用户组成员

把授权放在用户组上以后，新增人员只需加入用户组，移除人员只需删除组成员。删除组成员不会删除用户，也不会删除项目资源。

```command
[root@controller ~]# openstack group contains user bookops-group bookops-user
[root@controller ~]# openstack group user list bookops-group
```

## 14.2 Glance镜像运维

一．运维目标

1．理解镜像数据、镜像元数据和项目可见范围。

2．上传小型测试镜像并查询镜像状态。

3．修改镜像描述、保护属性和扩展属性。

4．创建实例快照后，区分基础镜像与快照镜像。

二．镜像对象与状态

1．镜像数据和元数据

Glance Image Service（Glance镜像服务）把镜像文件与镜像属性作为一个逻辑对象管理。镜像数据通常保存在文件系统、对象存储或分布式存储后端，Glance数据库保存名称、所有者、格式、状态、可见性、保护标志和扩展属性。客户端通过镜像标识访问对象，修改名称不会改变镜像标识。

disk_format描述虚拟磁盘格式，qcow2支持稀疏文件、快照和写时复制，raw结构简单、运行开销较小但通常占用更多实际空间。container_format描述镜像在传输时的封装方式，普通虚拟机磁盘通常使用bare。min_disk和min_ram给出使用镜像启动实例时的最低资源条件。

2．可见性和保护属性

private镜像只对所属项目可见；shared镜像通过成员关系共享给指定项目；community镜像可以被发现，但不会自动出现在所有项目的默认列表中；public镜像面向全部项目。protected为True时，删除请求会被拒绝，它保护的是镜像对象，不会自动复制镜像数据。

表14-2中的queued表示镜像记录已经建立但数据尚未写入；saving表示数据正在传输；active表示可以被Nova用于创建实例；killed表示数据写入失败。状态由Glance任务推进，不能用修改名称或属性的方法把失败镜像直接变为active。

使用image set修改描述、最小资源和保护属性。属性修改不会重写镜像数据，但会影响镜像能否删除以及Nova是否接受该镜像。

四．镜像删除边界

1．解除保护

受保护镜像必须先解除保护，再执行删除。解除保护前应确认没有仍需从该镜像重建的实例或自动化任务。

```command
[root@controller ~]# openstack image set --unprotected bookops-image
```

2．按对象标识删除

名称可能被修改或重复，清理时先取得镜像标识，再按标识删除。本章在Nova实例和Dashboard截图完成后再删除bookops-image。

```command
[root@controller ~]# IMAGE_ID=$(openstack image show bookops-image -f value -c id)
[root@controller ~]# openstack image delete $IMAGE_ID
```

## 14.3 Placement资源信息运维

一．运维目标

1．理解资源提供者、资源清单、特征、用量和分配的关系。

2．通过Placement API读取计算节点资源提供者。

3．查看VCPU、MEMORY_MB和DISK_GB的容量与用量。

4．认识generation并发控制编号，不人工改写Nova维护的资源记录。

二．Placement资源模型

1．资源提供者和资源清单

Placement Service（Placement资源放置服务）保存可供工作负载使用的资源事实。resource provider（资源提供者）可以是计算节点、共享存储池或其他资源池；inventory（资源清单）描述提供者能够供应的资源类别和容量。Nova计算节点通常登记VCPU、MEMORY_MB和DISK_GB三类标准资源。

资源清单不仅包含total，还包含reserved、min_unit、max_unit、step_size和allocation_ratio。total表示物理或逻辑总量，reserved预留给宿主机，allocation_ratio决定可超分配比例；min_unit、max_unit和step_size限定一次分配的最小值、最大值和步长。调度器必须同时满足这些约束。

2．特征、用量和分配

trait（特征）描述资源的定性能力，例如处理器指令集、虚拟化能力或存储类型。usage（用量）是某个提供者当前已被分配的资源数量；allocation（分配）把消费者与提供者上的资源数量关联起来。Nova实例通常是消费者，实例删除后相应分配应被释放。

generation是资源提供者的并发更新编号。更新资源清单或特征时，客户端要携带已经读取的generation；若其他操作先完成更新，旧generation会被拒绝，避免后写入的数据覆盖新状态。

五．Placement运维边界

Placement数据与Nova实例、迁移和资源跟踪紧密关联。人工修改提供者资源清单、特征或分配可能造成Nova数据库与Placement事实不一致。日常运维先从Nova服务和计算节点配置排查，再由组件维护流程更新Placement。本章只读取资源信息，不人工创建资源提供者或改写分配。

## 14.4 Nova实例、规格与配额运维

一．运维目标

1．查看Nova控制服务、计算服务和Hypervisor状态。

2．创建项目专用实例规格并检查项目访问范围。

3．创建实例，执行停止、启动、暂停、恢复和软重启。

4．创建实例快照，理解实例状态、任务状态和电源状态。

二．计算服务和实例对象

1．服务与Hypervisor

Nova Compute Service（Nova计算服务）由nova-api、nova-scheduler、nova-conductor、nova-novncproxy和nova-compute等进程协作。nova-api接收请求，nova-scheduler选择计算节点，nova-conductor协调数据库访问，nova-compute驱动Hypervisor完成实例操作，nova-novncproxy提供控制台代理。

compute service list中的Status表示管理员是否启用服务，State表示服务心跳是否正常。enabled/up说明服务既未被人为禁用，近期又能向控制面报告心跳。Hypervisor列表反映计算节点虚拟化驱动和资源状态，不等同于某台实例的运行状态。

2．实例规格、配额和实例

flavor（实例规格）定义虚拟处理器、内存和根磁盘等单台实例资源。quota（配额）限制一个项目能够使用的实例总数、虚拟处理器总数、内存、端口、网络和存储资源。规格决定“一台多大”，配额决定“最多能用多少”。

server（实例）引用镜像、规格、网络端口、安全组和可选卷。Nova保存实例的期望状态和调度位置，Glance提供镜像，Neutron创建端口，Placement建立资源分配，计算节点最终生成虚拟机。任何一个环节失败都可能使实例进入ERROR。

## 14.5 Neutron网络运维

一．运维目标

1．查看Linux bridge、DHCP、Metadata和L3等网络代理状态。

2．创建项目网络、子网、路由器和路由器接口。

3．建立安全组规则，查看实例端口和固定IP。

4．掌握端口、路由器接口、子网和网络的依赖清理顺序。

二．网络对象与代理

1．网络、子网和端口

Neutron Networking Service（Neutron网络服务）把二层连接、三层地址和访问策略拆分为不同对象。network（网络）表示逻辑二层广播域；subnet（子网）定义地址段、网关、地址池和域名服务器；port（端口）保存MAC地址、固定IP、安全组和计算节点绑定信息。

实例创建时，Nova请求Neutron建立端口，再把端口信息交给nova-compute。端口ACTIVE通常表示后端绑定已经建立，DOWN可能表示尚未绑定、实例停止或代理异常。删除网络前必须先删除或迁移引用该网络的端口。

2．路由器和安全组

router（虚拟路由器）连接一个或多个项目子网，也可以设置外部网关。路由器接口在Neutron中表现为特殊端口，因此删除子网前要先移除路由器接口。security group（安全组）是一组作用于端口的有状态规则；允许进入的连接会自动允许对应返回流量。

## 14.6 Cinder卷与快照运维

一．运维目标

1．查看Cinder调度服务、卷服务、可用区和卷类型。

2．创建卷并识别卷的异步状态。

3．创建卷快照，并由快照创建恢复卷。

4．理解卷连接对Nova、Cinder、计算节点和iSCSI数据通路的依赖。

二．卷服务、卷类型和后端

1．控制面与数据面

Cinder Block Storage Service（Cinder块存储服务）向实例提供独立于根磁盘的持久块设备。cinder-api接收请求，cinder-scheduler选择后端，cinder-volume调用LVM、Ceph或其他存储驱动创建实际卷。卷元数据位于Cinder数据库，卷数据位于存储后端。

本书双节点环境的cinder-volume运行在compute，使用/dev/sdb上的cinder-volumes卷组和LVM iSCSI后端。卷对象删除后，后端逻辑卷才被释放；仅删除数据库记录会留下无法管理的数据，因此不能绕过Cinder服务直接操作后端卷。

2．卷类型和可用区

volume type（卷类型）把用户请求映射到后端能力和扩展规格。可用区用于表达服务故障域或位置边界。本书环境使用lvm卷类型和nova可用区，名称相同不代表计算可用区与存储可用区一定由同一故障域实现。

五．卷连接与故障边界

1．连接前检查

把LVM iSCSI卷连接到实例时，Nova向Cinder取得连接信息，计算节点使用open-iscsi登录目标，再由libvirt把块设备加入实例。计算节点必须具有iscsiadm并运行iscsid，Cinder目标端口必须可达。

```command
[root@compute ~]# systemctl is-active iscsid
[root@compute ~]# systemctl is-active targetclid
[root@compute ~]# iscsiadm -m session
```

2．连接和卸载

只有上述数据通路正常时才执行连接。卷进入in-use且server volume list出现同一卷标识后，来宾系统才能识别新设备。若卷长期停在attaching，应停止重复提交，检查Nova事件、Cinder连接记录、iSCSI会话和计算节点日志；确认没有实际连接后再由管理员恢复对象状态。

```command
[root@controller ~]# source /root/bookops-openrc
[root@controller ~]# openstack server add volume bookops-server bookops-volume
[root@controller ~]# openstack server volume list bookops-server
[root@controller ~]# openstack server remove volume bookops-server bookops-volume
```

本章不在来宾系统中格式化卷，也不把连接异常写成卷数据成功挂载。块设备进入实例后，文件系统创建、挂载和数据写入属于来宾系统运维，应在确认设备标识和数据责任后另行实施。

六．卷和快照清理

先删除由快照产生的恢复卷，再删除快照和原卷。卷处于in-use时不能直接删除，必须先从实例卸载。

```command
[root@controller ~]# openstack volume delete bookops-volume-copy
[root@controller ~]# openstack volume snapshot delete bookops-volume-snapshot
[root@controller ~]# openstack volume delete bookops-volume
```

## 14.7 Swift容器与对象运维

一．运维目标

二．对象存储层次与一致性

1．账户、容器和对象

Swift Object Storage（Swift对象存储服务）面向对象名称和HTTP接口，不向用户提供可直接挂载的块设备。账户通常与Keystone项目对应，容器组织对象名称，对象保存数据和元数据。同一容器中的对象名称必须唯一，名称可以包含斜杠形成类似目录的展示效果，但Swift核心仍按完整对象名称管理。

对象数据由object-server保存，账户和容器索引分别由account-server和container-server维护，proxy-server接收用户请求并依据ring定位后端设备。ring保存分区到设备的映射，不保存用户对象内容。

2．元数据和副本

对象具有Content-Type、Content-Length、ETag和用户自定义元数据。ETag常用于内容完整性判断，但不能当作口令或访问凭据。Swift通过副本、后台复制和一致性校验处理节点故障；成功响应表示写入达到当前策略要求，后台进程继续维护副本一致性。

五．资源清理与运维责任

1．清理顺序

资源之间存在引用，清理必须从依赖链末端开始。表14-8给出bookops资源的清理顺序。

{{TABLE:表14-8}}

表14-8先处理实例和存储派生对象，再处理网络，最后处理镜像、规格和身份对象。清理前应重新查询对象标识、项目和名称；项目中存在非本章资源时，不得直接删除项目。

2．清理计算和存储资源

载入bookops用户环境，删除实例、实例快照、恢复卷、卷快照、原卷、Swift对象和容器。

```command
[root@controller ~]# source /root/bookops-openrc
[root@controller ~]# openstack server delete --wait bookops-server
[root@controller ~]# openstack image set --unprotected bookops-server-snapshot
[root@controller ~]# openstack image delete bookops-server-snapshot
[root@controller ~]# openstack volume delete bookops-volume-copy
[root@controller ~]# openstack volume snapshot delete bookops-volume-snapshot
[root@controller ~]# openstack volume delete bookops-volume
[root@controller ~]# openstack object delete bookops-container bookops-object.txt
[root@controller ~]# openstack container delete bookops-container
```

3．清理网络、规格和镜像

```command
[root@controller ~]# openstack router remove subnet bookops-router bookops-subnet
[root@controller ~]# openstack router delete bookops-router
[root@controller ~]# openstack subnet delete bookops-subnet
[root@controller ~]# openstack network delete bookops-net
[root@controller ~]# openstack security group delete bookops-secgroup
[root@controller ~]# source /root/admin-openrc
[root@controller ~]# openstack flavor delete bookops-flavor
[root@controller ~]# openstack image set --unprotected bookops-image
[root@controller ~]# openstack image delete bookops-image
```

4．清理身份对象

先撤销项目角色，再删除用户组、用户和项目。user角色若由本章创建且没有其他授权，可以删除；若平台原已使用该角色，则只撤销bookops项目授权，不删除全局角色。

```command
[root@controller ~]# openstack role remove --project bookops --group bookops-group user
[root@controller ~]# openstack role remove --project bookops --group bookops-group member
[root@controller ~]# openstack group remove user bookops-group bookops-user
[root@controller ~]# openstack group delete bookops-group
[root@controller ~]# openstack user delete bookops-user
[root@controller ~]# openstack project delete bookops
[root@controller ~]# rm -f /root/bookops-openrc
```

六．最小权限与资源责任

云平台运维同时涉及计算资源、网络边界、用户数据和业务连续性。使用独立项目和普通用户执行日常操作，可以把管理员权限限制在身份建立、跨项目查询和最终清理等必要环节。操作前核对对象标识和依赖关系，操作后确认状态和资源归属，是云平台工程质量的重要组成部分。

开放基础设施由多个社区组件协同完成，也由众多开发者、测试人员和运维人员共同维护。平台使用者既要掌握命令和界面，也要尊重数据权属、遵循最小权限、保留必要记录并承担操作后果。严谨、可追溯、可恢复的工作方式体现工程人员的责任意识和工匠精神。
