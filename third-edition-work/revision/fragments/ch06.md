# 第六章 Keystone的安装及其配置

本章导读：本章介绍OpenStack身份服务Keystone的基本功能、核心对象和工作过程，并在第五章基础服务已经就绪的环境中完成Keystone的手工安装与配置。Keystone是各项OpenStack服务共同依赖的身份入口。用户访问镜像、计算、网络或存储服务之前，需要先提交凭据取得令牌；客户端还要通过服务目录找到目标服务的访问地址。

可以把OpenStack云平台比作一间屋子，把Keystone比作屋子的“大门”。来访者先说明自己是谁，再用能够证明身份的凭据取得一把有时效的“钥匙”，随后才能进入对应房间。本章沿着“大门与钥匙”的比喻，学习Domain、Project、Group、Role、Token、Service、Endpoint、Catalog和Policy等Identity API v3概念，并把这些概念与Antelope实验环境中的实际对象对应起来。

全部操作在controller逐条输入，配置文件使用vi手工编辑，数据库、密钥仓、初始身份对象、服务条目和三类端点均按实际依赖顺序建立。完成本章后，平台便具备统一身份入口和服务目录，可继续安装镜像服务。

## 6.1 Keystone功能详解

一．Keystone简介

1．统一身份入口

Keystone是OpenStack的Identity服务。若把云平台比作一间由许多房间组成的屋子，Keystone就是进入屋子的“大门”。来访者首先要说明自己是谁，并出示能够证明身份的凭据。Keystone受理认证请求后，根据用户、作用域和角色形成认证结果，并签发具有有效期的令牌。客户端随后携带令牌访问其他OpenStack服务。

屋子里的计算、镜像、网络和存储服务也各有自己的“门”。Keystone并不代替这些服务完成业务操作，而是提供统一的身份入口和服务目录。目标服务收到请求后，会读取令牌中的身份、作用域和角色信息，再结合自身策略决定该操作是否允许。因此，Keystone负责认证和身份对象管理，各业务服务负责执行自己的授权策略，二者不能混为一谈。

身份认证回答“你是谁”。用户提交用户名、密码等凭据后，Keystone依据已保存的身份信息处理认证。授权则回答“你在什么范围内能做什么”。用户要在某个项目或域中取得角色，目标服务再根据策略解释该角色对应哪些操作。仅仅存在一个用户，并不表示该用户天然拥有某个项目的管理权限。

Keystone还维护服务目录。OpenStack由多个相对独立的服务组成，客户端若不知道镜像、计算或网络服务的地址，就无法向它们发送请求。每个服务在Keystone中登记服务条目，并为公有、内部和管理三种接口登记端点。认证成功后，客户端可以从服务目录获得这些访问地址。

Antelope使用身份接口第3版。本书统一使用项目表示资源边界，不使用第2版身份接口中的旧租户术语和旧管理员入口配置；三类Keystone端点都使用http://controller:5000/v3/。这三个地址在双节点实验环境中相同，生产环境可以让不同接口使用不同网络路径。

2．认证、授权与服务发现

二．Keystone中的基本概念

1．域、项目、用户、组与角色

Domain（域）是Identity API v3中的管理边界和命名空间。用户、组和项目都属于某个域，不同域可以出现名称相同但身份不同的对象。域还可以作为委派管理的边界，让某个组织管理自己域内的用户与项目。本实验使用Keystone初始化时建立的Default域，后续服务用户和service项目也放在该域中。

Project（项目）是OpenStack组织资源所有权、隔离关系和配额的主要边界。一个项目可以对应一个客户、一个组织、一门课程的实验小组或某项业务。虚拟机、网络、卷等资源通常归属于项目。用户不是因为被创建就自动拥有项目权限，而是要在某个项目作用域中取得角色授权。

User（用户）代表人员、系统或服务的数字身份。管理员是用户，普通云平台使用者是用户，Glance、Nova和Neutron等组件访问其他服务时也使用各自的服务用户。服务用户与Linux系统用户、MariaDB数据库用户和RabbitMQ账户属于不同系统，即使名称相同，也不能互相替代。

Group（组）是同一域中若干用户的集合。管理员可以把角色授予一个组，使组内成员在指定项目或域作用域中继承相应授权。组用于集中管理身份，项目用于组织资源边界，二者解决的问题不同。不能把一组用户简单等同于一个项目，也不能用组替代项目配额。

Role（角色）是授权关系中的名称或标签。Keystone把某个角色授予某个作用域中的用户或组，形成“身份对象—作用域—角色”的关系。角色本身不包含一套固定不变的业务命令权限；Nova、Glance、Neutron等目标服务会按照自己的策略解释角色与请求属性。因而，“拥有admin角色”与“绕过所有策略”不是同一含义。

2．令牌、服务、端点与服务目录

令牌是Keystone在凭据认证成功后签发的、有有效期的承载式访问凭据。令牌可以表达用户身份、项目或域作用域、角色以及服务目录。客户端访问其他服务时携带令牌，目标服务据此取得认证上下文。令牌应当像临时钥匙一样受到保护，不能在截图、共享文档或公开日志中显示完整值。

服务是登记在Keystone中的逻辑API服务条目。例如，Keystone对应identity服务，Glance对应image服务，Nova对应compute服务，Neutron对应network服务。服务条目描述“这是什么服务”，但仅有服务名称还不足以让客户端完成访问，还需要端点给出实际网络地址。

端点是访问某项服务API的网络地址。端点记录区域、接口类型和URL。公有接口通常面向最终用户或外部客户端，内部接口通常供内部服务或管理网络使用，管理接口表达管理访问入口的语义。管理接口同样需要身份认证和策略判断，不会自动获得最高权限。

服务目录是服务与端点的有组织集合。客户端取得认证结果后，可以根据服务类型、区域和接口类型从目录中选择地址。服务条目没有端点时，客户端知道平台存在某项服务，却无法发现访问位置；端点没有正确关联服务时，也不能形成完整目录。因此，后续每个组件都要同时创建服务条目和三类端点。

策略把角色、作用域和请求属性映射到具体API操作。Keystone负责管理用户、项目和角色授权，目标服务依据策略决定是否接受请求。策略可以使用服务代码内的默认规则，也可以通过policy.yaml进行调整。实验环境沿用发行版默认策略，生产平台则按照职责分离和最小权限原则设计角色与策略。

区域用于标识一组服务端点所在的逻辑范围。本实验把所有端点登记在RegionOne。区域名称不是主机名，也不是网络地址；一个区域可以包含多个服务，一个云平台也可以规划多个区域。客户端在服务目录中结合区域与接口类型选择适合的端点。

三．Keystone的认证与服务发现过程

1．凭据认证与令牌签发

用户使用OpenStackClient发起请求时，客户端先读取环境变量中的认证地址、域、项目、用户名和口令。Keystone接收凭据后识别用户，并根据所请求的作用域取得角色授权。认证成功后，Keystone签发令牌，并在认证结果中提供相应的服务目录。

客户端访问Glance、Nova或Neutron时，从目录中选择目标服务的Endpoint，再把令牌随请求发送给目标服务。目标服务通过中间件取得令牌对应的认证信息，结合自己的Policy处理请求。业务结果由目标服务返回，Keystone不会替代Nova创建实例，也不会替代Neutron建立网络。

2．业务服务访问

这种工作方式把统一身份入口与各业务服务解耦。用户不必为每个组件单独维护一套身份，服务也不必各自实现完整的用户目录。与此同时，每个业务服务仍保留自己的策略边界，避免把整个云平台的业务授权集中为一条不可区分的规则。

服务用户也遵循同样过程。后续创建glance、placement、nova、neutron和cinder用户时，会把这些用户加入service项目，并授予合适角色。组件在配置文件中保存自己的服务用户凭据，使用Keystone取得令牌，再访问所依赖的其他服务。service项目因此成为承载服务身份作用域的重要项目，而不是保存服务程序文件的目录。

图6.2给出了从OpenStackClient到Keystone再到业务服务的访问过程。客户端先提交凭据，Keystone返回令牌和服务目录；客户端选择目标端点并携带令牌访问业务服务，业务服务依据策略处理请求。

## 6.2 Keystone的令牌、密钥与Web承载

Keystone需要把身份对象持久化到MariaDB，把频繁使用的数据交给缓存机制，并通过Web服务器对外提供Identity API。理解这三类依赖，可以解释本章为什么必须先完成第五章，再按照“数据库—配置—同步—密钥—初始化—Web承载”的顺序部署。

一．令牌与密钥

1．Fernet令牌

本书在keystone.conf的[token]段设置provider = fernet。Fernet令牌包含经过加密和签名保护的认证信息，不需要把每一枚令牌逐条保存到数据库。Keystone仍然需要数据库保存用户、项目、角色和服务目录等持久化对象，也需要妥善保管用于加密与解密令牌的Fernet密钥。

Fernet令牌具有有效期，客户端应在有效期内携带它访问服务。密钥仓中的密钥属于敏感材料，不应复制到普通文档或显示在截图中。单控制节点实验只需在controller初始化密钥仓；多控制节点生产环境还要设计密钥轮换和安全分发机制，使各Keystone节点拥有一致的有效密钥集合。

2．Credential密钥

Credential密钥用于保护Keystone保存的凭据数据，与Fernet令牌密钥承担不同职责。keystone-manage credential_setup建立Credential密钥仓，keystone-manage fernet_setup建立Fernet密钥仓。两条命令都需要指定keystone系统用户和用户组，使服务进程能够读取密钥文件。

Memcached也不能替代这两类密钥。缓存保存的是可以重新生成的运行时数据，密钥仓保存的是保护令牌或凭据所需的密码材料，MariaDB保存的是身份与目录等持久化对象。把三者分别理解，可以避免在故障处理或系统迁移时错误地删除关键材料。

二．数据库同步与初始化

1．数据库同步

Keystone软件包携带数据库迁移内容。创建空的keystone数据库并写好连接参数后，使用keystone-manage db_sync建立当前Antelope版本所需的表、索引和约束。该操作必须以keystone系统用户身份执行，使运行环境和文件权限与服务保持一致。

数据库同步属于部署过程，不是把配置文件复制到数据库。keystone.conf中的connection参数告诉Keystone怎样连接MariaDB，迁移内容则定义数据库结构。完成同步后，Keystone才能在后续bootstrap过程中写入Default域、管理员身份、服务和端点等初始对象。

2．Bootstrap初始化

keystone-manage bootstrap用于建立Keystone首次运行所需的初始身份和目录对象。本书明确给出管理员用户名、项目名、角色名、identity服务名、三类端点、区域与统一实验口令。该命令会初始化Default域中的admin用户和admin项目，建立初始角色授权，同时登记Keystone自身的identity服务及public、internal、admin三类端点。

由于bootstrap已经创建Keystone服务和端点，后面不能再次手工创建同名identity服务或重复端点。后续Glance、Placement、Nova等组件不使用Keystone bootstrap，而是逐条创建服务用户、角色授权、服务条目和三类端点。理解这一区别，可以保留身份对象的完整创建过程，并避免Keystone自身出现重复对象。

三．Apache与管理员环境

1．Apache与WSGI

Antelope实验中的Keystone API由Apache HTTP Server通过WSGI承载。openstack-keystone软件包提供Keystone应用，httpd提供Web服务器，python3-mod_wsgi软件包提供发行版所需的WSGI模块。这里的软件包名称只是运行时组件名称，本章不涉及程序设计。

Apache的ServerName设置为controller，使Web服务器使用与实验拓扑一致的主机名。/usr/share/keystone/wsgi-keystone.conf定义Keystone WSGI入口，把它链接到/etc/httpd/conf.d/后，Apache启动时即可加载Keystone API配置。本发行版不需要另外启动名为keystone.service的系统服务，也不使用旧版35357端口配置。

2．管理员环境文件

OpenStackClient需要知道认证地址和管理员身份信息。若每次输入命令都重复书写域、项目、用户名、口令和Region参数，既冗长又容易出现不一致。因此，本书使用/root/admin-openrc集中保存实验环境管理员变量，并在需要执行OpenStack命令时手工加载。

admin-openrc包含明文实验口令，应限制文件权限。生产环境不能把统一管理员口令长期保存在多人可读文件中，应采用受控的凭据获取、最小权限账户和秘密管理机制。管理员环境也不应被误用为所有服务的公共凭据，后续组件仍要建立各自的服务用户。

## 6.3 实训项目3 Keystone的手工安装与配置

一．实训前提环境

已经完成实训项目2的全部内容。controller上的MariaDB、RabbitMQ和Memcached已经配置并启动，OpenStackClient已经安装；controller与compute的主机名解析、管理网络、软件仓和时间基础沿用第四章配置。

本章使用qwer1234作为数据库用户、Keystone管理员和环境文件中的实验口令。

二．实训涉及节点

Keystone数据库、服务程序、密钥仓、Apache承载和管理员环境文件都在controller完成。compute在本章不执行安装命令。操作过程中应根据[root@controller ~]#、MariaDB [(none)]>和->提示符区分Linux终端、数据库客户端与SQL续行环境。

三．实训目标

1．完成Keystone数据库、三个来源账户和数据库权限配置。

2．完成Keystone、Apache和WSGI组件安装与配置文件编辑。

3．完成Keystone数据库同步及Fernet、Credential密钥初始化。

4．完成管理员身份、identity服务和三类端点初始化。

5．完成管理员环境文件、service项目和Apache服务启动。

四．实训步骤及其详解

步骤一：创建Keystone数据库及数据库用户

Keystone需要独立数据库保存身份对象、角色授权和服务目录。首先使用MariaDB root账户从controller本机进入数据库客户端。

```command
[root@controller ~]# mysql -uroot -pqwer1234
```

看到MariaDB [(none)]>提示符后，先建立名为keystone的数据库。

```command
MariaDB [(none)]> CREATE DATABASE keystone;
```

接着分别创建允许从localhost、127.0.0.1和其他管理网络地址连接的keystone数据库账户。三条账户使用相同名称和实验口令，但MariaDB会根据连接来源分别匹配它们。

```command
MariaDB [(none)]> CREATE USER 'keystone'@'localhost' IDENTIFIED BY 'qwer1234';
MariaDB [(none)]> CREATE USER 'keystone'@'127.0.0.1' IDENTIFIED BY 'qwer1234';
MariaDB [(none)]> CREATE USER 'keystone'@'%' IDENTIFIED BY 'qwer1234';
```

数据库与用户创建后，把keystone数据库中的全部表权限授予这三个账户。下面把每条GRANT分为两行输入，MariaDB显示的->表示当前SQL尚未以分号结束。

```command
MariaDB [(none)]> GRANT ALL PRIVILEGES ON keystone.*
    -> TO 'keystone'@'localhost';
MariaDB [(none)]> GRANT ALL PRIVILEGES ON keystone.*
    -> TO 'keystone'@'127.0.0.1';
MariaDB [(none)]> GRANT ALL PRIVILEGES ON keystone.*
    -> TO 'keystone'@'%';
```

最后重新载入权限表并退出数据库客户端，回到controller的Linux终端。

```command
MariaDB [(none)]> FLUSH PRIVILEGES;
MariaDB [(none)]> EXIT;
```

这里的数据库名、数据库用户名和Keystone服务名称都写为keystone，但它们属于不同对象。数据库保存数据，数据库用户取得数据库访问权，Keystone服务则在后面的服务目录中登记身份API。配置时必须根据对象所在系统理解相同名称。

步骤二：安装Keystone和Apache组件

数据库准备完成后，从openstack-local软件仓安装Keystone、Apache和WSGI运行时组件。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo='openstack-local' install openstack-keystone httpd python3-mod_wsgi
```

openstack-keystone提供Antelope版本的身份服务文件和管理工具，httpd承载Identity API，python3-mod_wsgi提供openEuler软件包环境中的WSGI模块。三者共同组成本实验的Keystone服务端。

步骤三：手工编辑Keystone主配置文件

使用vi打开/etc/keystone/keystone.conf。本章只修改数据库连接与令牌提供者两个必要配置段，其他参数沿用发行包默认值。

```command
[root@controller ~]# vi /etc/keystone/keystone.conf
```

在[database]段写入数据库连接。127.0.0.1表示Keystone与MariaDB位于同一controller，keystone:qwer1234分别是数据库用户名和实验口令，末尾的keystone是数据库名称。

```config
[database]
connection = mysql+pymysql://keystone:qwer1234@127.0.0.1/keystone
```

在[token]段选择Fernet令牌提供者。

```config
[token]
provider = fernet
```

若文件原有段落中存在其他生效的connection或provider，应在vi中注释旧值，只保留本实验的一条有效配置。qwer1234不含连接URL保留字符，可以直接写入连接串。

步骤四：同步Keystone数据库

主配置文件保存后，以keystone系统用户身份执行数据库同步。su的-s参数指定Shell，-c参数指定要执行的Keystone管理命令，最后的keystone表示切换到该系统用户。

```command
[root@controller ~]# su -s /bin/sh -c "keystone-manage db_sync" keystone
```

该操作把Antelope版本需要的表、索引和约束写入空的keystone数据库，为后续初始化身份对象做好结构准备。数据库结构建立后，继续初始化两类密钥仓。

步骤五：初始化Fernet与Credential密钥仓

首先建立Fernet密钥仓，并把文件属主和属组设置为keystone，使身份服务可以使用这些密钥签发和读取Fernet令牌。

```command
[root@controller ~]# keystone-manage fernet_setup --keystone-user keystone --keystone-group keystone
```

接着建立Credential密钥仓，用于保护Keystone保存的凭据数据。

```command
[root@controller ~]# keystone-manage credential_setup --keystone-user keystone --keystone-group keystone
```

两类密钥仓只在首次部署时初始化。教材不显示密钥文件内容，也不把密钥复制到图片或其他节点。若将来建设多控制节点平台，应另行设计受控的密钥分发与轮换方案。

步骤六：初始化管理员身份、服务和三类端点

使用keystone-manage bootstrap建立Keystone首次运行所需的身份与目录对象。下面把管理员用户名、项目名、角色名和服务名明确写出，使每个参数的对象关系清晰。

```command
[root@controller ~]# keystone-manage bootstrap --bootstrap-password qwer1234 --bootstrap-username admin --bootstrap-project-name admin --bootstrap-role-name admin --bootstrap-service-name keystone --bootstrap-admin-url http://controller:5000/v3/ --bootstrap-internal-url http://controller:5000/v3/ --bootstrap-public-url http://controller:5000/v3/ --bootstrap-region-id RegionOne
```

bootstrap在Default域中建立admin用户和admin项目，并把admin角色授予该管理员身份；同时登记名称为keystone、类型为identity的服务，在RegionOne中创建public、internal和admin三类端点。三类URL在本实验中都指向controller的5000端口和v3路径。

数据库、用户、服务和端点在这里分别对应不同层次：keystone数据库及数据库用户已经由MariaDB创建，admin是Keystone身份用户，keystone是服务目录中的identity服务，三个URL是关联该服务的Endpoint。区分这些对象，是后续手工注册其他OpenStack组件的基础。

步骤七：配置Apache与Keystone WSGI

使用vi打开Apache主配置文件，把ServerName设置为controller。主机名应与第四章的/etc/hosts解析一致。

```command
[root@controller ~]# vi /etc/httpd/conf/httpd.conf
```

在配置文件中加入或修改以下内容。

```config
ServerName controller
```

保存后，为Keystone提供的WSGI配置建立链接，使Apache能够加载身份服务入口。

```command
[root@controller ~]# ln -s /usr/share/keystone/wsgi-keystone.conf /etc/httpd/conf.d/wsgi-keystone.conf
```

链接左侧是openstack-keystone软件包提供的配置文件，右侧是Apache自动加载的conf.d目录。本发行版通过httpd承载Keystone，不另行启动keystone.service。

步骤八：创建管理员环境变量文件

Keystone初始对象已经写入数据库，接下来使用vi创建/root/admin-openrc，保存OpenStackClient进行管理员认证所需的环境变量。

```command
[root@controller ~]# vi /root/admin-openrc
```

在文件中写入以下内容。Default的大小写与bootstrap建立的域名称保持一致，认证地址使用Identity API v3，Region使用RegionOne。

```config
export OS_PROJECT_DOMAIN_NAME=Default
export OS_USER_DOMAIN_NAME=Default
export OS_PROJECT_NAME=admin
export OS_USERNAME=admin
export OS_PASSWORD=qwer1234
export OS_AUTH_URL=http://controller:5000/v3
export OS_IDENTITY_API_VERSION=3
export OS_IMAGE_API_VERSION=2
export OS_REGION_NAME=RegionOne
```

环境文件包含管理员实验口令，因此把权限设置为仅root可读写。

```command
[root@controller ~]# chmod 600 /root/admin-openrc
```

步骤九：启用并启动Apache承载的Keystone服务

Apache与WSGI配置完成、管理员环境文件准备后，先把httpd加入开机启动，再启动当前服务。启动httpd也就启动了本实验的Keystone API承载环境。

```command
[root@controller ~]# systemctl enable httpd.service
[root@controller ~]# systemctl start httpd.service
```

Antelope在本实验中统一使用5000端口提供Identity API，不再配置旧版独立管理员端口。服务启动后即可加载管理员环境，继续创建后续组件共同使用的service项目。

步骤十：加载管理员环境并创建service项目

使用点命令在当前Shell中读取/root/admin-openrc，使后续openstack命令取得管理员认证参数。

```command
[root@controller ~]# . /root/admin-openrc
```

接着在Default域中创建service项目。该项目用于承载后续Glance、Placement、Nova、Neutron和Cinder等组件的服务用户作用域。

```command
[root@controller ~]# openstack project create --domain default --description "Service Project" service
```

service项目不是Linux目录，也不是系统服务集合。后续章节会分别创建组件服务用户，把角色授予这些用户在service项目中的身份，再创建Service和public、internal、admin三类Endpoint。至此，Keystone的数据库、配置、密钥、初始身份、服务目录、Web承载、管理员环境和service项目已经完成。下一章将在这套身份基础上安装Glance镜像服务。
