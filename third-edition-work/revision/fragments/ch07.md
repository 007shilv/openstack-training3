# 第七章 Glance的安装及其配置

本章导读：本章介绍OpenStack镜像服务Glance的基本功能、组成结构和镜像生命周期，并在前六章已经完成的控制节点上手工安装和配置Glance。镜像是创建云主机的重要基础。一个能够使用的镜像不仅包含虚拟磁盘数据，还应具有名称、格式、状态、可见性、最小资源要求等元数据。Glance把这些信息组织起来，并通过统一接口为Nova、Horizon和OpenStackClient提供镜像注册、查询和数据传输能力。

学习Glance可以从镜像文件与镜像服务的关系入手，再逐步认识文件系统和对象存储后端、镜像格式以及镜像状态。本章按照这条路径讲解OpenStack 2023.1 Antelope中的Glance服务结构和配置方式。当前实验在controller启用本地文件系统后端，使用enabled_backends和default_backend选择名为file的后端；独立glance-registry属于早期架构，本实验采用glance-api直接组织元数据与后端访问的部署方式。

实训采用“实训前提环境—实训涉及节点—实训目标—实训步骤及其详解”的学习结构。全部命令在controller逐条输入，数据库账户按照localhost、127.0.0.1和%三种来源分别创建，服务用户、角色授权、image服务和RegionOne中的三类端点逐项建立。随后完成glance-api.conf编辑、数据库同步以及API服务启用和启动，为后续镜像资源运维准备服务基础。

本书使用qwer1234作为Glance数据库用户和服务用户的统一课堂口令。该弱口令只适用于无生产数据、无公网入口并可随时重置的隔离教学环境。生产云平台必须分别管理数据库凭据和服务凭据，限制配置文件读取权限，并使用高强度口令、秘密管理和定期轮换机制。

## 7.1 Glance功能简介

Glance是OpenStack的Image服务。云平台中的“镜像”可以理解为创建虚拟机磁盘的基础模板。它通常包含已经安装好的操作系统，也可以进一步包含驱动、运行库和业务软件。使用统一镜像创建实例，可以减少重复安装操作，使同一批虚拟机具有相近的软件基础，并为扩容、迁移和灾后恢复提供可重复使用的起点。

Glance提供镜像发现、注册、元数据管理和镜像数据传输等能力。用户可以通过OpenStackClient或Horizon向Glance提交镜像信息，Nova在创建实例时也会从Glance取得镜像元数据和镜像数据。Glance并不负责选择计算节点，也不负责运行虚拟机；Nova完成计算调度和实例生命周期管理，Glance专注于镜像这一类资源。把二者职责分开，可以避免把“保存模板”和“运行实例”理解为同一过程。

镜像服务同时面对两类内容。第一类是镜像元数据，例如镜像名称、唯一标识、所有者、状态、可见性、磁盘格式、容器格式、字节大小、创建时间、更新时间、最小内存和最小磁盘要求。第二类是镜像数据，即真正构成虚拟磁盘内容的字节流。元数据保存在Glance数据库中，镜像数据则由Glance Store访问所配置的存储后端。数据库记录不能替代镜像文件，镜像文件也不能脱离元数据直接成为云平台中的镜像对象。

一. Glance的基本组成

Glance采用客户端—服务器结构，通过REST API接收请求。客户端可以是OpenStackClient、Horizon、Nova，也可以是其他经过授权的OpenStack服务。请求进入glance-api后，首先经过身份认证与策略处理，再由Glance内部的领域控制逻辑完成元数据、配额、通知、位置和存储等操作。

glance-api是本实验直接部署的服务进程。它向用户和其他组件提供镜像API，接收镜像对象创建、元数据访问以及镜像数据上传和下载等请求。glance-api根据配置文件连接Keystone、Memcached、MariaDB和镜像后端。Keystone负责认证上下文，Memcached承接认证中间件所需的缓存，MariaDB保存镜像记录，后端目录保存镜像数据。

Glance数据库保存镜像对象及其相关元数据。数据库中的images表记录镜像主体信息，其他表用于保存位置、成员、属性、标签和任务等关联内容。数据库同步由当前Glance软件包提供的迁移内容完成，学习者不需要手工设计这些表。数据库与后端目录必须共同受到保护，因为其中任一部分丢失都会破坏镜像对象的完整性。

glance_store库为Glance访问不同存储后端提供统一接口。管理员可以根据部署规模选择文件系统、Ceph RBD、Swift、Cinder等后端。Glance通过统一的后端接口组织数据访问，用户不需要根据每一种存储分别学习一套镜像API。后端选择属于云平台架构决策，应结合容量、并发、高可用、数据保护和运维能力综合考虑。

早期版本常把glance-registry描述为Glance的独立核心服务。它曾位于API与数据库访问之间，组织对镜像元数据的访问。随着Glance架构演进，独立Registry服务已经不再是本书Antelope实验需要部署的服务。本章只安装和启动openstack-glance-api，不编辑glance-registry.conf，也不创建openstack-glance-registry服务单元。学习旧资料时应先辨认版本，不能把历史组件机械带入新环境。

二. 镜像元数据

镜像的ID是平台内部识别镜像对象的唯一标识。镜像名称便于人员阅读，却不应被当作永远唯一的主键。用户可能建立同名镜像，也可能在镜像升级后保留旧版本。不同服务之间传递对象关系时通常使用ID，教材中的人工操作则同时显示名称和ID，帮助读者建立“显示名称”和“唯一标识”的区别。

visibility表示镜像的可见范围。public镜像可以供云平台中符合策略的项目发现和使用，private镜像主要属于创建它的项目，shared镜像可以通过成员关系共享给指定项目，community镜像则允许被发现但不表示已经经过平台管理员背书。可见性控制的是发现和使用范围，不能替代镜像内容审查、软件许可检查或安全扫描。

protected属性用于限制镜像被随意删除。它适合标记教学基准镜像或平台公共镜像，但不能理解为数据已经形成独立备份。若唯一文件后端损坏，protected并不会自动复制镜像数据。生产平台仍要依靠高可用存储、备份、异地保护和恢复演练保证镜像可持续使用。

min_disk和min_ram描述使用该镜像创建实例时所需的最低磁盘和内存。Nova选择实例规格和计算资源时会结合这些信息处理请求。若元数据把最低资源写得过小，实例可能在启动后因空间或内存不足而无法正常工作；写得过大，又会无端限制可用规格。因此，镜像制作人员应根据操作系统和预装软件的真实需求填写这些属性。

镜像属性还可以记录操作系统类型、发行版、版本、架构、虚拟化要求和启动方式等信息。属性越规范，调度、运维和用户选择就越清晰。可信云平台不应只关心“文件能否上传”，还应建立镜像来源、版本、许可证、补丁和责任人的记录。对国产操作系统镜像进行规范命名和来源追溯，既便于教学复现，也体现对开源许可、软件供应链和数据安全的职业责任。

三. 镜像状态

镜像对象从创建到可用会经历状态变化。queued表示镜像标识已经保留，但镜像数据尚未上传；saving表示镜像数据正在写入Glance；active表示数据已经就绪，镜像可以供后续服务使用。对于直接上传的常规路径，这三个状态构成最容易观察的主线：先登记对象，再传输数据，最后成为可用镜像。

Glance还支持分阶段导入。uploading表示数据已经进入导入暂存过程，importing表示Glance正在执行镜像导入处理，成功后进入active。分阶段导入适合需要格式检查、转换或其他导入处理的场景。它与直接向queued镜像写入数据的路径不同，同一个镜像对象不应同时混用两种上传过程。

deactivated表示非管理员用户暂时不能取得镜像数据，但镜像记录仍然保留。重新激活后可以回到active。killed表示镜像数据上传过程中发生错误且镜像不可读；deleted表示镜像已经不可用，相关记录将在后续清理；pending_delete表示采用延迟删除时，镜像数据尚未最终移除但对象已经不能恢复使用。

状态不是供管理员随意填写的备注，而是Glance在镜像生命周期中维护的控制信息。不同状态决定用户能否下载、使用或继续处理镜像。排查镜像问题时，应先理解当前状态所处的生命周期位置，再分析数据传输、后端空间、权限或任务处理等原因，不能只把所有非active状态概括为“上传失败”。

四. 磁盘格式与容器格式

disk_format描述虚拟磁盘数据本身采用的格式。Glance支持raw、qcow2、vhd、vhdx、vmdk、vdi、iso、ploop以及aki、ari、ami等标识。某种格式能被Glance登记，不等于所有计算驱动和虚拟化程序都能使用它。管理员必须同时考虑Nova所用虚拟化后端、镜像制作工具以及目标工作负载的兼容性。

raw格式结构简单，可以近似理解为块设备内容的直接映像。它容易被多种工具处理，读写路径也较直接，但文件表面大小通常接近虚拟磁盘容量，存储和传输成本需要结合稀疏文件与后端能力评估。raw不是“天然更安全”或“永远更快”，实际效果仍取决于存储、缓存和虚拟化配置。

qcow2是KVM环境中常见的写时复制磁盘格式。它支持动态增长和Copy on Write，相同虚拟容量下文件通常比完整展开的raw镜像小，便于教学环境保存和传输。qcow2还具有快照、压缩等能力，但格式层功能会带来额外元数据处理。生产环境选择raw还是qcow2，应通过具体存储架构和性能要求决定，而不是只依据文件大小。

container_format描述镜像数据外面是否存在包含虚拟机元数据的封装。bare表示没有额外的容器或元数据封套，是OpenStack教学中最常用的取值。ovf和ova用于表达开放虚拟化格式及其归档封装，aki、ari、ami与相应的Amazon镜像类型有关。Glance不会仅凭container_format就证明文件内容与声明完全一致，真正使用镜像的服务还必须支持该格式。

## 7.2 Glance后端与调用过程

用户创建实例时，Nova先根据请求中的镜像ID取得镜像元数据，了解镜像状态、格式、最小资源要求和访问范围。随后，计算服务按照实例创建流程取得镜像数据并准备虚拟机磁盘。Glance在这一过程中提供镜像信息和数据入口，但计算节点选择、资源分配和虚拟机启动仍由Nova完成。

Glance收到客户端请求后，通过Keystone认证中间件取得请求者的身份、项目和角色信息，再由策略判断该请求可以执行哪些镜像操作。镜像元数据通过数据库访问层写入MariaDB，镜像数据通过glance_store写入后端。服务目录中的image端点告诉客户端怎样找到glance-api，配置文件中的Keystone参数则告诉Glance怎样处理来自客户端的认证信息。

一. 文件系统后端

文件系统后端把镜像数据保存到Glance节点的指定目录。本实验使用/var/lib/glance/images/，其优点是结构直观、部署依赖少，适合双节点教学环境观察Glance与后端之间的关系。controller既运行glance-api，又保存镜像数据，因此不需要在本章增加独立存储节点。

本实验在[DEFAULT]段设置enabled_backends = file:file。等号左侧的file是管理员为后端选定的标识，冒号右侧的file是后端驱动类型。在[glance_store]段把default_backend设置为file，表示未另外指定后端时使用这个标识；[file]段再给出filesystem_store_datadir，使标识、驱动和实际目录形成完整关系。

虽然实验只启用一个文件后端，仍采用Antelope支持的多后端配置形式。这样可以让读者理解：enabled_backends负责声明可用后端，default_backend负责选择默认后端，每个后端标识对应一个配置段。将来扩展RBD或Swift时，应为新后端规划独立标识与参数，而不是把不同存储目录混写在同一文件后端中。

文件系统后端的不足也很明显。若controller磁盘损坏或目录不可用，镜像数据会受到直接影响；单节点目录还会限制横向扩展和高可用。生产环境常采用共享存储、Ceph RBD、Swift等后端，并设计冗余、备份和恢复流程。教材选择文件系统是为了突出组件关系，不代表它是所有规模云平台的最佳方案。

二. 数据库、身份与后端的依赖顺序

Glance数据库必须先于数据库同步建立。glance-api.conf中的connection给出数据库账户、口令、地址和数据库名，glance-manage db_sync再根据该连接把Antelope所需的数据结构写入数据库。若先同步再写连接，管理命令无法找到正确数据库；若把数据库root账户写入组件配置，又会破坏组件账户隔离。

Keystone中的glance用户是服务身份，不是操作系统用户或数据库用户。glance系统用户用于运行服务进程并访问本地文件，glance数据库用户用于连接MariaDB，Keystone中的glance用户用于服务认证。三个对象名称相同是为了便于识别，但它们分属Linux、MariaDB和Keystone三个身份空间，必须分别创建或由软件包提供。

image服务条目说明Glance是一项镜像服务，三个Endpoint说明客户端从哪里访问它。本实验在RegionOne中把public、internal和admin都指向http://controller:9292。三个URL相同是双节点教学网络的简化，三种接口的语义仍然不同。生产部署可以根据外部网络、内部服务网络和管理网络分别规划地址与访问控制。

配置完成后，数据库同步先建立持久化结构，openstack-glance-api服务再开始对外承载请求。把启动动作放在最后，可以使服务第一次启动时已经具备数据库连接、认证参数和后端目录。部署顺序看似只是若干命令的排列，实质上反映了“依赖先准备、配置后落地、服务最后启动”的工程逻辑。

## 7.3 实训项目4 Glance的手工安装与配置

一．实训前提环境：

已经完成实训项目3的全部内容。controller上的MariaDB、Memcached、Apache和Keystone已经启动，/root/admin-openrc与service项目已经建立，openstack-local教学仓可以使用。本实训从第六章结束后的教学快照继续进行。

本章继续使用qwer1234作为Glance数据库账户和Keystone服务用户的课堂口令。该口令只允许用于可重置的隔离实验环境。配置文件中包含明文服务口令，课堂结束后不应把文件、终端记录或截图发布到公共网络。

二．实训涉及节点：

Glance数据库、身份对象、服务程序、配置文件、数据库同步和文件系统后端都在controller完成。compute将在后续Nova章节承担计算服务任务。操作时应根据[root@controller ~]#、MariaDB [(none)]>和->提示符区分Linux终端、数据库客户端和SQL续行环境。

三．实训目标：

理解Glance的镜像元数据、状态、格式、API和存储后端；创建Glance数据库以及localhost、127.0.0.1和%三种来源的数据库用户并授权；创建glance服务用户及其admin角色授权；登记image服务和RegionOne中的public、internal、admin三个端点；安装openstack-glance软件包；使用vi手工编辑glance-api.conf；同步数据库；启用并启动openstack-glance-api服务。

四．实训步骤及其详解：

步骤一：创建Glance数据库及数据库用户

Glance使用独立数据库保存镜像元数据。首先在controller使用MariaDB root账户进入数据库客户端。

```command
[root@controller ~]# mysql -uroot -pqwer1234
```

看到MariaDB [(none)]>提示符后，创建名为glance的数据库。

```command
MariaDB [(none)]> CREATE DATABASE glance;
```

接着为本地主机名、本地TCP地址和其他允许来源分别创建glance数据库用户。三条账户使用相同课堂口令，但MariaDB会根据连接来源分别匹配。

```command
MariaDB [(none)]> CREATE USER 'glance'@'localhost' IDENTIFIED BY 'qwer1234';
MariaDB [(none)]> CREATE USER 'glance'@'127.0.0.1' IDENTIFIED BY 'qwer1234';
MariaDB [(none)]> CREATE USER 'glance'@'%' IDENTIFIED BY 'qwer1234';
```

为三个账户授予glance数据库的全部操作权限。下面把GRANT语句分两行输入，->是MariaDB客户端显示的续行提示符。

```command
MariaDB [(none)]> GRANT ALL PRIVILEGES ON glance.*
    -> TO 'glance'@'localhost';
MariaDB [(none)]> GRANT ALL PRIVILEGES ON glance.*
    -> TO 'glance'@'127.0.0.1';
MariaDB [(none)]> GRANT ALL PRIVILEGES ON glance.*
    -> TO 'glance'@'%';
```

重新载入权限表并退出数据库客户端。

```command
MariaDB [(none)]> FLUSH PRIVILEGES;
MariaDB [(none)]> EXIT;
```

glance数据库用于保存元数据，glance数据库用户用于组件连接MariaDB。后面还会出现Linux系统用户和Keystone服务用户，不能因为名称相同就省略其中任何一类对象。

步骤二：创建Glance服务用户及角色授权

先在当前Shell加载管理员环境变量，使openstack命令取得管理员身份和服务目录信息。

```command
[root@controller ~]# . /root/admin-openrc
```

在Default域创建glance用户，口令与本书课堂口令保持一致。

```command
[root@controller ~]# openstack user create --domain default --password qwer1234 glance
```

把admin角色授予glance用户在service项目中的身份。该授权使Glance以服务用户身份访问所需的OpenStack服务，不等于创建数据库权限。

```command
[root@controller ~]# openstack role add --project service --user glance admin
```

步骤三：创建image服务和三类端点

在Keystone服务目录中创建名称为glance、类型为image的服务条目。服务名称便于管理员识别，服务类型供客户端在目录中定位镜像服务。

```command
[root@controller ~]# openstack service create --name glance --description "OpenStack Image" image
```

接着在RegionOne中依次创建public、internal和admin端点。本实验的三类接口都使用controller的9292端口。

```command
[root@controller ~]# openstack endpoint create --region RegionOne image public http://controller:9292
[root@controller ~]# openstack endpoint create --region RegionOne image internal http://controller:9292
[root@controller ~]# openstack endpoint create --region RegionOne image admin http://controller:9292
```

服务条目回答“这是什么服务”，端点回答“从哪里访问服务”。只有把image服务与三个端点共同登记到目录中，客户端才能按照区域和接口类型选择Glance地址。

步骤四：安装Glance软件包

从openstack-local教学仓安装OpenStack 2023.1 Antelope的Glance软件包。

```command
[root@controller ~]# dnf -y --disablerepo='*' --enablerepo='openstack-local' install openstack-glance
```

软件包提供glance-api服务程序、glance-manage管理命令、默认配置文件和文件后端目录。本实验不安装独立glance-registry服务。

步骤五：手工编辑Glance主配置文件

使用vi打开/etc/glance/glance-api.conf。配置内容按功能分为数据库连接、Keystone认证、API认证方式和文件后端四组。

```command
[root@controller ~]# vi /etc/glance/glance-api.conf
```

在文件中写入或修改以下配置段。若原文件中存在同名参数，应在vi中注释旧值，只保留本实验的一条有效配置。

```config
[DEFAULT]
enabled_backends = file:file

[database]
connection = mysql+pymysql://glance:qwer1234@127.0.0.1/glance

[keystone_authtoken]
www_authenticate_uri = http://controller:5000
auth_url = http://controller:5000
memcached_servers = controller:11211
auth_type = password
project_domain_name = Default
user_domain_name = Default
project_name = service
username = glance
password = qwer1234

[paste_deploy]
flavor = keystone

[glance_store]
default_backend = file

[file]
filesystem_store_datadir = /var/lib/glance/images/
```

[database]段中的127.0.0.1表示MariaDB与Glance位于同一controller，连接串首尾两个glance分别是数据库用户名和数据库名称。[keystone_authtoken]段使用第六章创建的服务用户向Keystone处理认证，项目为service，域为Default，缓存地址为controller:11211。

[paste_deploy]段选择keystone认证方式。[DEFAULT]段声明标识为file、类型为file的后端，[glance_store]段把它设为默认后端，[file]段指定镜像数据目录。三个配置段中的file含义彼此关联，拼写必须保持一致。

配置文件包含服务口令，保存后把属组和权限设置为Glance服务可以读取、其他普通用户不能读取。

```command
[root@controller ~]# chown root:glance /etc/glance/glance-api.conf
[root@controller ~]# chmod 640 /etc/glance/glance-api.conf
```

步骤六：同步Glance数据库

主配置文件完成后，以glance系统用户身份执行数据库同步。该操作根据Antelope版本的迁移内容，在空的glance数据库中建立镜像、位置、成员、属性、标签和任务等数据结构。

```command
[root@controller ~]# su -s /bin/sh -c "glance-manage db_sync" glance
```

数据库同步负责建立Glance持久化结构，镜像数据仍由文件系统后端保存。完成同步后即可进入服务启动步骤，后续运维章节将继续讲解镜像资源的创建与管理。

步骤七：启用并启动Glance API服务

首先把openstack-glance-api加入开机启动，然后启动当前服务。两条命令分开输入，便于区分“下次开机自动启动”和“本次立即运行”。

```command
[root@controller ~]# systemctl enable openstack-glance-api.service
[root@controller ~]# systemctl start openstack-glance-api.service
```

服务启动时会读取glance-api.conf，通过127.0.0.1连接glance数据库，通过Keystone处理认证，并把镜像数据写入/var/lib/glance/images/。完成这些操作后，信创云平台已经具备镜像服务基础。后续运维章节将在这一环境中继续学习镜像的上传、查看、修改、下载和删除，使本章建立的元数据、状态、格式与后端概念落实到完整的镜像生命周期管理中。
