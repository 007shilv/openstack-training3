# 第十章 Neutron的安装及其配置

本章导读：Neutron为OpenStack提供网络即服务能力，把物理网卡、Linux网桥、虚拟端口、子网、路由器和安全组组织成统一网络对象。Nova负责创建实例，Neutron负责把实例接口接入正确网络，并通过DHCP、路由和元数据服务提供地址与通信条件。

本书采用Linux Bridge和ML2插件构建Provider网络与VXLAN租户网络。controller运行Neutron Server及控制类代理，controller和compute都运行Linux Bridge代理；两台主机的ens34不配置IP地址，专门连接外部二层Provider网络。

{{FIGURE:图10.1}}

图10.1中，neutron-server集中处理网络对象和API请求，DHCP、L3与Metadata代理在controller创建网络命名空间，Linux Bridge代理分别在两台节点上连接虚拟端口。ens33承担管理和隧道通信，ens34直接映射到provider物理网络。

## 10.1 Neutron功能与网络模型

一．Neutron Server与插件

1．API与数据库

neutron-server是网络服务的控制入口，接收网络、子网、端口、路由器和安全组请求，并把对象状态保存到neutron数据库。它通过Keystone完成身份认证，通过RabbitMQ与各节点代理交换状态和任务。

Neutron控制面只描述逻辑网络，不直接搬运实例数据。实例数据由计算节点网桥、隧道接口、物理网卡和网络命名空间转发，因此API可用与实例通信正常是两个不同层面。

2．ML2与机制驱动

ML2（Modular Layer 2，模块化二层）把网络类型与具体转发机制分开。本书启用flat和VXLAN两种类型，使用Linux Bridge机制驱动。flat网络对应外部二层网络，VXLAN用于不同节点之间的租户网络封装。

ML2配置决定可以创建哪些网络类型、租户默认使用什么网络以及VNI范围。Linux Bridge代理配置决定provider名称映射到哪块物理网卡，并指定VXLAN隧道使用的本地管理地址。

二．网络代理

1．Linux Bridge、DHCP与Metadata

Linux Bridge（Linux网桥）代理在节点上创建网桥和虚拟接口，把实例tap接口接入Neutron端口。DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）代理为子网中的实例分配地址、网关和域名服务器信息。

Metadata代理把实例访问169.254.169.254的请求转交给Nova元数据服务。实例可以通过元数据取得主机名、密钥等初始化信息。Metadata代理与Nova必须使用相同的共享口令，本书统一设置为qwer1234。

2．L3与路由

L3代理负责虚拟路由器、网络地址转换和浮动IP路径。它通常在controller创建路由器命名空间，把租户网络连接到Provider网络。Provider网络本身可以直接承载外部地址，租户网络则通过虚拟路由器访问外部网络。

## 10.2 Provider网络与VXLAN网络

一．Provider网络

1．物理映射

Provider网络把Neutron中的逻辑名称provider映射到ens34。ens34保持无IP地址，由Linux Bridge代理接管并加入网桥。宿主机不通过ens34配置管理地址，可避免宿主网络栈与实例外部网络混在同一接口上。

controller和compute都配置physical_interface_mappings = provider:ens34。这样实例无论被调度到哪一节点，其Provider端口都能进入相同物理二层网络。

2．外部网络路径

实例的Provider网络端口通过tap设备进入Linux网桥，再由ens34进入外部交换网络。该路径不经过VXLAN封装，适合直接使用外部二层地址或承载租户路由器的外部网关。

二．VXLAN租户网络

1．覆盖网络

VXLAN（Virtual Extensible LAN，虚拟扩展局域网）把二层以太网帧封装在三层网络中，使不同计算节点上的实例能够处于同一逻辑网络。封装流量在本书环境中通过ens33管理网络传输，controller使用192.168.234.151，compute使用192.168.234.150作为local_ip。

VNI（VXLAN Network Identifier，VXLAN网络标识符）用于区分不同租户网络。本书把VNI范围设为1:1000，Neutron在该范围内为VXLAN网络分配标识。

MTU（Maximum Transmission Unit，最大传输单元）表示一帧或一个数据包在链路上无需分片即可承载的最大长度。VXLAN会增加封装头部，本书把租户网络MTU设为1450，以便封装后的数据通过1500字节的底层网络。

2．网络命名空间

DHCP和L3代理通过Linux网络命名空间隔离不同网络功能。DHCP命名空间运行dnsmasq，路由器命名空间保存租户路由与网络地址转换规则。命名空间使同一主机能够同时处理多个项目网络而不混淆接口和路由表。

## 10.3 端口绑定与网络状态同步

Neutron数据库保存的是用户希望得到的逻辑网络，真正的数据包却要经过计算节点网卡、Linux Bridge、VXLAN设备、网络命名空间和物理交换网络。端口绑定把逻辑端口与具体主机上的转发设施连接起来；代理同步则持续比较期望状态与实际状态，使网络在服务重启或消息丢失后重新收敛。

一．ML2端口绑定

1．类型驱动与机制驱动

ML2（Modular Layer 2，模块化二层插件）把“网络采用什么分段方式”和“主机怎样实现这种网络”分开。类型驱动处理flat、VLAN、VXLAN等网络类型及其分段标识，机制驱动负责把端口落实到Linux Bridge、Open vSwitch、SR-IOV或其他网络后端。

创建网络时，类型驱动检查网络类型和物理网络名称，并在需要时分配VLAN ID或VXLAN Network Identifier（VNI，VXLAN网络标识）。创建端口时，Neutron先在数据库保存逻辑记录，再根据端口目标主机、网卡类型、网络分段和机制驱动能力执行绑定。

ML2操作包含precommit和postcommit两个阶段。precommit在数据库事务中检查并保存Neutron状态；postcommit在数据库提交以后通知机制驱动改变外部网络后端。这样可以避免数据库最终回滚，而外部交换机或虚拟交换设备已经提前改变，造成两边状态不一致。

端口绑定结果包含host_id、vif_type、vif_details、profile和状态等信息。host_id说明端口准备在哪个计算主机使用，vif_type说明Nova应建立哪类虚拟接口，vif_details提供桥接、插接或安全组相关参数。若没有机制驱动能够处理该端口，vif_type会出现binding_failed。

2．绑定状态的变化

新端口通常从DOWN开始。Nova确定目标计算主机后更新端口绑定信息，Neutron进入绑定过程，端口可处于BUILD。机制驱动生成绑定结果，二层代理在目标主机发现虚拟接口并完成桥接、安全组和网络分段配置后，端口进入ACTIVE。

ACTIVE表示Neutron已经完成所需配置并收到代理确认，不等于应用层业务一定可达。安全组规则、DHCP地址、路由、名称解析和来宾操作系统网卡仍可能影响通信。网络排错应从端口状态继续沿数据路径逐层分析。

实例删除或端口迁移时，Neutron按绑定层次的相反顺序拆除。内层主机接口先释放，外层网络结构后释放，可以避免底层通道已经消失而上层端口仍试图发送数据。多层绑定场景中，这种“先建立外层、后建立内层；先拆内层、后拆外层”的顺序尤其重要。

二．Provider与VXLAN的分支

1．Provider网络路径

Provider网络把Neutron逻辑网络映射到管理员已经存在的物理网络。本书使用physical_interface_mappings把provider映射到compute的ens34。端口绑定时，Linux Bridge机制驱动在实例接口与物理网卡之间建立桥接，数据帧可以直接进入外部二层网络。

Provider网络不需要VXLAN封装，路径较短，但广播域、地址规划和二层隔离依赖外部网络。管理员需要协调物理交换机、网段、网关和DHCP边界。把错误物理接口映射为provider，可能使管理网络和实例外部流量混在一起，甚至导致节点失联。

2．VXLAN租户网络路径

租户网络使用VXLAN（Virtual Extensible LAN，虚拟可扩展局域网）在IP网络之上建立二层覆盖网络。端口的数据帧先进入本地主机的Linux Bridge，再封装为带VNI的UDP报文，通过管理网络到达另一节点，解封装后进入目标租户网络。

VNI把不同租户网络隔离，隧道端点IP决定封装报文从哪个节点地址发送。VXLAN解决了跨主机二层连接和大规模分段问题，但增加封装开销，并依赖节点之间的IP可达性。VNI、local_ip或MTU配置错误，都可能使端口显示存在却无法正常传输数据。

Provider和VXLAN不是互相排斥的整个平台选择。云平台可以同时提供外部Provider网络和内部租户网络，再通过L3代理的虚拟路由器连接二者。实例端口绑定先根据所属网络类型进入不同二层路径，跨网段或访问外部时再进入三层路由、网络地址转换和浮动IP处理。

三．代理同步与状态收敛

1．期望状态与实际状态

Neutron Server在数据库中保存网络、子网、端口、路由器和安全组的期望状态。Linux Bridge代理、DHCP代理、L3代理和Metadata代理运行在相应节点，把期望状态转换为Linux网络设备、命名空间、地址、路由和过滤规则。

二层代理周期性扫描本地主机上的设备，并通过RPC（Remote Procedure Call，远程过程调用）向Neutron Server查询端口详情。发现新设备后配置桥、网络分段和安全组，再上报设备已上线；发现设备消失后，清理相关状态并上报DOWN。

消息队列可以及时通知代理配置变化，但分布式系统不能假定每条消息永远不会丢失。代理重启、网络短暂中断或队列拥塞后，周期扫描会重新取得完整事实并修正本地状态。事件通知提高响应速度，周期同步提供最终收敛保障。

2．异常分支与重试

若代理发现端口却无法取得详情，可能是数据库记录尚未提交、RPC暂时失败或端口已经删除。代理不会凭本地接口名称自行猜测全部配置，而是在下一轮重新查询。若机制驱动返回binding_failed，Nova不能把该接口作为可用虚拟网卡继续启动实例。

DHCP代理为网络建立服务端口和命名空间，根据子网配置提供地址；L3代理建立路由器命名空间、接口、路由和网络地址转换；Metadata代理把实例对169.254.169.254的请求转发到Nova Metadata服务，并携带能够标识实例的上下文。任何一类代理异常都会影响不同阶段，不能统称为“Neutron服务故障”。

端口长期停留在DOWN或BUILD时，应先确认目标主机的二层代理是否正常，再检查机制驱动绑定结果、主机映射、桥和虚拟接口。实例已经ACTIVE但不能取得地址时，应继续检查DHCP代理；内部通信正常但不能访问外部时，再检查路由器、L3代理和Provider网络。

3．地址、路由与元数据支路

二层端口进入ACTIVE只说明虚拟接口已经接入相应网络，并不表示所有三层服务都已完成。启用DHCP的子网需要DHCP代理建立服务端口、地址配置和命名空间，实例启动后通过广播取得地址。关闭DHCP时，端口仍可以完成绑定，但实例必须使用静态地址或由其他地址服务负责配置，因此“没有收到DHCP地址”不一定表示二层绑定失败。

需要跨子网通信时，L3代理把虚拟路由器接口落实到命名空间，并根据外部网关和浮动IP配置路由与地址转换。元数据请求则从实例的链路本地地址进入Metadata代理，再转发给Nova元数据服务。一个实例能够访问同网段邻居，却不能访问外网或元数据，说明二层路径大体成立，后续检查应转向路由器、地址转换、Provider网络或元数据支路。

端口绑定结果同时受逻辑网络和主机条件影响。网络类型决定需要建立的二层结构，物理网络映射决定Provider网络能够落到哪块接口，主机上的代理类型和运行状态决定机制驱动是否能够接受该端口。控制面完成绑定后，代理还要把安全组、网桥端口和转发表落实到主机。数据库记录已经更新而主机尚未完成配置时，端口仍可能处于BUILD或DOWN状态。

四．工程责任与安全边界

虚拟网络把大量业务隔离建立在配置之上。一个物理网卡映射、VNI范围或安全组规则的错误，可能同时影响多个项目。网络工程人员既要理解数据包路径，也要对变更范围、回退方案和业务连续性负责，不能把“命令执行成功”当成安全边界已经正确。

云平台网络建设还体现协同责任。平台人员需要与机房网络、安全和应用团队共同确认地址、路由、带宽和访问策略。准确记录接口关系、坚持最小开放、保护管理网络并审慎处理每次变更，是保障数字基础设施可靠运行的工程素养。

## 10.4 实训项目7 Neutron的手工安装与配置

一．实训前提环境

Nova控制服务和nova-compute已经部署，controller与compute的ens34均处于无IP地址状态。教材配套本地软件仓保持启用，RabbitMQ、Keystone和MariaDB在controller运行。

二．实训涉及节点

controller安装neutron-server、ML2、Linux Bridge、DHCP、L3和Metadata组件；compute只安装Linux Bridge代理。必须先完成controller数据库、身份、配置与服务，再配置compute。

三．实训目标

1．完成neutron数据库、三个来源账户和数据库授权。

2．完成neutron服务用户、admin角色授权、network服务和三个端点创建。

3．完成controller上的Neutron、ML2、Linux Bridge、DHCP、L3和Metadata配置。

4．完成Neutron数据库同步及控制节点服务的顺序启动。

5．完成compute上的Linux Bridge代理配置和服务启动。
