# 第十二章 Swift的安装及其配置

本章导读：Swift为OpenStack提供对象存储服务。对象存储不把数据表现为传统磁盘分区或文件系统目录，而是通过账户、容器和对象三级名称空间保存数据，并通过HTTP接口访问。它适合镜像、备份、日志和非结构化文件等数据。

本书在controller部署代理服务并生成Ring文件，在compute使用50 GiB独立磁盘/dev/sdc部署账户、容器和对象服务。数据磁盘格式化为XFS文件系统，标签为swift-data。已有的/dev/sdb继续归Cinder使用，两块数据盘职责不能互换。

图12.1表示Swift在双节点环境中的组件分布。controller上的代理服务处理认证和请求转发，compute上的存储服务直接读写/dev/sdc。Ring文件在控制节点生成后复制到存储节点，用于计算对象应保存的位置。

{{FIGURE:图12.1}}

图12.1中，Proxy Server（代理服务器）是客户端入口；Account Server（账户服务器）、Container Server（容器服务器）和Object Server（对象服务器）分别维护账户、容器和对象数据。Ring不是集中式数据库，而是一组确定对象位置的映射文件。

## 12.1 Swift对象模型与组件

一．对象模型

1．账户、容器与对象

账户对应一个项目的对象存储名称空间，容器用于组织对象，对象由名称、数据和元数据组成。容器与传统文件夹相似但不是文件系统目录，对象名称中可以包含斜杠，从而在客户端界面中形成层次感。

2．对象数据与元数据

对象数据保存在存储节点的数据目录中，账户和容器服务维护对象清单及关系信息。对象通过HTTP上传和下载，不需要客户端挂载块设备。对象一旦以同名重新上传，其内容会被替换，因此应用需要根据业务要求管理版本和生命周期。

二．服务组件

1．代理服务

代理服务接收客户端请求，通过Keystone完成身份认证，再依据Ring把请求发送到相应存储服务。它屏蔽后端节点和磁盘分布，使客户端只需要访问controller:8080上的统一入口。

2．账户、容器和对象服务

账户服务记录容器清单，容器服务记录对象清单，对象服务保存对象数据。三类服务使用不同端口，分别为6202、6201和6200。rsync服务用于节点间数据同步和恢复，本书单存储节点仍配置该服务，以保持Swift的标准组件关系。

## 12.2 Ring与对象访问过程

一．Ring结构

1．分区、区域和设备

Ring把对象名称散列为分区，再把分区映射到区域、节点和设备。区域用于表达故障隔离范围，节点由IP地址和端口标识，设备对应实际存储目录。本书只有一个存储节点，因此副本数设为1；生产环境通常需要多个区域和多个副本。

2．Ring生成与分发

账户、容器和对象分别使用account、container和object三类Ring。管理员在controller创建builder文件、加入compute上的sdc设备并执行重平衡，然后把生成的ring.gz文件复制到compute。两端Ring必须一致，否则代理服务和存储服务会对对象位置产生不同判断。

二．对象请求过程

## 12.3 副本一致性与后台维护

Swift面向大量对象和节点故障设计。客户端请求不必等待所有副本完全一致才返回，系统通过Ring选择主设备，通过法定成功响应判断请求结果，并依靠复制、审计、更新和清理等后台进程不断修复差异。这种机制使单个磁盘或节点故障不必立即中断整个对象服务。

一．从对象名称到存储设备

1．哈希、分区与副本

Swift把账户、容器和对象路径组合后计算哈希，再从哈希中取得若干位作为分区号。分区（Partition，把哈希空间划分后的管理单位）不是磁盘分区，而是一组对象位置的逻辑编号。Ring记录每个分区的副本应该位于哪些设备。

分区数量由partition power决定，数量等于2的相应次方。分区数通常远多于设备数，使数据移动可以按分区批量进行，而不必逐个对象重新计算全部位置。副本数决定每个分区由多少份设备位置负责。

设备按照region、zone、server和device形成故障域。Ring优先把同一分区的不同副本放到不同故障域，降低一台服务器、一个机架或一个站点故障同时丢失全部副本的概率。设备weight表示相对容量，Ring重平衡时按权重分配分区副本。

本书双节点环境只有一块Swift数据盘，并把副本数设为1，只用于展示组件关系和手工过程。生产环境通常需要至少三个适当隔离的存储节点，并根据故障域设计副本或纠删码策略。单副本环境没有节点级冗余，不能代表生产数据保护能力。

2．Ring分发与版本一致

账户、容器和对象使用不同Ring。管理员使用builder文件维护设备、权重和分区分配，执行rebalance后生成服务器读取的ring.gz文件。builder包含以后继续调整Ring所需的信息，ring.gz是运行时优化后的映射，两者用途不同。

所有代理和存储节点应使用同一轮生成的Ring。若某节点仍保存旧Ring，它对部分分区可能选择旧设备，Proxy和后台进程需要通过handoff与复制修复偏差。长期混用不同Ring会增加不必要的数据移动和请求失败，因此Ring变更必须按计划分发。

增加设备、删除设备或调整权重后，rebalance不会在一次变更中随意搬动所有副本。Ring尽量限制分区移动，并避免同一分区的多个副本同时迁移。这样可以降低扩容时的网络与磁盘冲击，让后台复制逐步完成新布局。

二．Proxy的请求判定

1．PUT写入与handoff

客户端向Proxy发送PUT对象请求。Proxy先通过账户、容器和对象Ring确定主设备，再把对象数据流式发送到相应Object Server。Proxy不会先把完整对象暂存在本地磁盘后再复制，而是处于客户端与存储服务之间的数据通道。

主设备不可用时，Proxy从Ring取得handoff node（交接节点，主设备故障时临时接收分区副本的设备）。Handoff保存的数据不是新的永久布局，主设备恢复后，Replicator会把数据移动到正确位置并清理临时副本。

在多副本环境中，Proxy根据配置要求的成功响应数量判断写入是否可以向客户端返回成功。少数副本暂时失败不一定使整个请求失败，但后台必须继续修复缺失副本。若成功响应不足，客户端收到失败，已经写入的部分副本仍需由一致性机制处理。

本书单副本环境只有一个目标设备，任何目标故障都会直接影响写入。这个限制有助于理解为什么生产Swift强调故障域和副本，而不是把多节点仅看作容量叠加。

2．GET读取与响应选择

读取对象时，Proxy通过Ring选择副本，并尝试取得可用响应。若首选设备不可达，可以继续访问其他主副本或handoff副本。响应头中的时间戳帮助系统识别较新的对象版本和删除标记。

Swift中的删除使用tombstone（删除标记，表示对象在某时间点已被删除的记录）参与副本同步。若只从一个设备移除文件，而其他副本仍保存旧对象，后台复制可能把旧数据重新带回。删除标记把“对象已经删除”作为一种需要传播的状态。

对象列表来自容器数据库，对象数据来自Object Server。对象数据已经写入而容器列表尚未更新时，短时间内可能出现对象可按名称读取却暂未出现在列表中的情况。Updater会补齐这些异步更新，形成最终一致的列表。

三．后台进程的修复循环

1．复制与审计

Replicator（副本同步进程）周期性扫描本地分区，与其他副本比较哈希或数据库变化，把缺失或较新的数据发送到正确设备。Ring变更、节点恢复或handoff数据回迁都依赖复制循环。一次扫描结束后，进程等待下一周期继续检查。

Object Auditor（对象审计进程）持续读取对象数据和元数据，检查文件是否可读、元数据是否完整以及校验结果是否一致。发现损坏对象时，审计进程把异常副本隔离，随后由复制进程从其他健康副本补回。审计负责发现，复制负责恢复，二者职责不同。

Account Auditor和Container Auditor检查账户、容器数据库的完整性。数据库复制使用变化同步保持多副本一致。大规模集群不可能依靠一次全量停机检查完成保护，因此这些进程以有限批次持续运行。

2．更新、清理与到期

Object Updater处理对象写入后未能及时送达容器数据库的更新，把异步pending记录重新发送给Container Server。Container Updater把容器统计信息发送到账户数据库。两个更新过程使对象、容器和账户三层视图逐步一致。

Object Expirer（到期对象清理进程）根据对象设置的到期时间发出删除操作。Container Sharder在超大容器场景把对象名称空间分片，减轻单个容器数据库压力。Reconstructor用于纠删码存储策略，根据片段和校验信息恢复缺失数据；本书单副本实验不启用纠删码。

后台进程需要控制并发、扫描速率和磁盘占用。运行过慢会延长不一致窗口，运行过快又会与前台请求争夺磁盘和网络。生产运维需要结合容量、故障恢复目标和业务峰谷调整周期，并监控未完成工作量。

3．时间戳与删除标记

Swift用时间戳比较对象的不同版本。写入、元数据更新和删除都带有时间信息，节点重新通信后按时间顺序判断哪个结果更新。由于各节点独立处理请求，稳定的时间同步非常重要；时间偏差过大可能使较旧的数据被误认为更新结果，也会增加副本收敛的复杂度。

删除对象时，存储节点不会只把数据文件移除，而是写入删除标记（Tombstone，对象已经删除的时间记录）。复制器把删除标记传播到其他副本，防止暂时离线的旧副本重新上线后使对象“复活”。删除标记保留到超过回收周期后才被清理。由此可见，删除在对象存储中也是一次需要跨副本传播的状态变化，而不是单个目录中的文件操作。

{{FIGURE:图12.3}}

图12.3中的前台路径追求在允许故障范围内及时返回，后台回环追求副本最终收敛。二者结合才构成Swift的可靠性。只观察一次PUT成功，不能代替对Ring、副本和后台进程的持续管理。

写入请求到达代理服务后，代理依据Ring选择主节点并并行发送数据。达到存储策略要求的成功数量后，客户端可以得到成功响应；暂时不可达的主节点由handoff节点代替。读取时，代理根据多个响应的时间戳和状态选择有效结果，必要时触发读修复。这样的处理使单个设备或节点故障不会立即中断对象访问，同时也把副本恢复工作交给后续后台进程。

Ring发生调整时，分区归属会变化，但对象不会在更新Ring文件的瞬间自动搬迁。复制器按照新旧位置比较分区，逐步把数据移到新的主节点，并在达到安全条件后清理临时副本。容量扩展、设备维护和故障恢复都依赖这一渐进过程，因此Ring文件、后台进程和设备状态必须保持一致。

## 12.4 实训项目9 Swift的手工安装与配置

一．实训目标

1．完成Swift服务用户、对象存储服务和三个端点的创建。

2．完成controller节点代理服务、共享配置和三类Ring的配置。

3．确认compute节点/dev/sdc为50 GiB独立数据盘，并建立XFS对象存储目录。

4．完成compute节点账户、容器、对象和rsync服务的配置与启动。

二．创建身份对象

1．创建服务用户和服务目录

Swift不使用MariaDB保存对象目录，因此本节不创建业务数据库。载入管理员环境变量后创建swift用户，并把它加入service项目。

```command
[root@controller ~]# source /root/admin-openrc
[root@controller ~]# openstack user create --domain Default --password qwer1234 swift
[root@controller ~]# openstack role add --project service --user swift admin
[root@controller ~]# openstack service create --name swift --description "OpenStack Object Storage" object-store
```

2．创建服务端点

对象存储端点包含项目标识，代理服务根据认证后的项目形成账户名称。

```command
[root@controller ~]# openstack endpoint create --region RegionOne object-store public "http://controller:8080/v1/AUTH_%(project_id)s"
[root@controller ~]# openstack endpoint create --region RegionOne object-store internal "http://controller:8080/v1/AUTH_%(project_id)s"
[root@controller ~]# openstack endpoint create --region RegionOne object-store admin "http://controller:8080/v1/AUTH_%(project_id)s"
```

三．配置controller节点

1．安装软件包并编辑共享配置

controller节点安装Swift代理服务软件，并在swift.conf中设置各节点共同使用的哈希前缀、哈希后缀和存储策略。共享参数将参与对象路径计算，因此后续复制到存储节点的swift.conf应与controller保持一致。

```command
[root@controller ~]# dnf -y install openstack-swift openstack-swift-proxy
[root@controller ~]# mkdir -p /etc/swift
[root@controller ~]# vi /etc/swift/swift.conf
```

```config
[swift-hash]
swift_hash_path_suffix = qwer1234
swift_hash_path_prefix = qwer1234

[storage-policy:0]
name = Policy-0
default = yes
```

2．编辑代理服务配置

proxy-server.conf定义代理服务的监听端口、请求处理流水线以及身份认证方式。客户端请求先经过健康检查、代理日志和Keystone认证，再由代理服务依据账户、容器和对象名称查找Ring并访问相应存储节点。

```command
[root@controller ~]# vi /etc/swift/proxy-server.conf
```

```config
[DEFAULT]
bind_port = 8080
user = swift
swift_dir = /etc/swift

[pipeline:main]
pipeline = catch_errors gatekeeper healthcheck proxy-logging cache container_sync bulk ratelimit authtoken keystoneauth staticweb copy formpost tempurl container-quotas account-quotas slo dlo versioned_writes proxy-logging proxy-server

[app:proxy-server]
use = egg:swift#proxy
account_autocreate = True

[filter:authtoken]
paste.filter_factory = keystonemiddleware.auth_token:filter_factory
www_authenticate_uri = http://controller:5000
auth_url = http://controller:5000
memcached_servers = controller:11211
auth_type = password
project_domain_name = Default
user_domain_name = Default
project_name = service
username = swift
password = qwer1234
delay_auth_decision = True

[filter:keystoneauth]
use = egg:swift#keystoneauth
operator_roles = admin,user,member

[filter:cache]
use = egg:swift#memcache
memcache_servers = controller:11211
```

四．创建并分发Ring

1．创建Ring并加入存储设备

在/etc/swift目录创建三类Ring。参数10表示分区幂次，1表示一个副本，最后一个1表示分区移动的最小时间间隔为1小时。

```command
[root@controller ~]# cd /etc/swift
[root@controller swift]# swift-ring-builder account.builder create 10 1 1
[root@controller swift]# swift-ring-builder container.builder create 10 1 1
[root@controller swift]# swift-ring-builder object.builder create 10 1 1
[root@controller swift]# swift-ring-builder account.builder add --region 1 --zone 1 --ip 192.168.234.150 --port 6202 --device sdc --weight 100
[root@controller swift]# swift-ring-builder container.builder add --region 1 --zone 1 --ip 192.168.234.150 --port 6201 --device sdc --weight 100
[root@controller swift]# swift-ring-builder object.builder add --region 1 --zone 1 --ip 192.168.234.150 --port 6200 --device sdc --weight 100
[root@controller swift]# swift-ring-builder account.builder rebalance
[root@controller swift]# swift-ring-builder container.builder rebalance
[root@controller swift]# swift-ring-builder object.builder rebalance
```

2．复制配置和Ring文件

确认compute的SSH主机指纹后，从controller把共享配置和Ring复制到compute。

```command
[root@controller swift]# scp /etc/swift/swift.conf compute:/etc/swift/swift.conf
[root@controller swift]# scp /etc/swift/account.ring.gz compute:/etc/swift/account.ring.gz
[root@controller swift]# scp /etc/swift/container.ring.gz compute:/etc/swift/container.ring.gz
```

五．配置compute节点

1．确认并格式化/dev/sdc

查看块设备、挂载点、签名和LVM信息，确认/dev/sdb仍属于cinder-volumes，/dev/sdc为50 GiB独立空白盘且不是系统盘。

```command
[root@compute ~]# lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
[root@compute ~]# findmnt -n -o SOURCE /
[root@compute ~]# pvs -o pv_name,vg_name
[root@compute ~]# wipefs --no-act /dev/sdc
[root@compute ~]# blkid -p /dev/sdc
```

只有/dev/sdc确认为空白盘时，才输入YES并创建XFS文件系统。

```command
[root@compute ~]# read -p "确认格式化/dev/sdc，输入YES：" ANSWER
[root@compute ~]# test "$ANSWER" = "YES"
[root@compute ~]# mkfs.xfs -f -L swift-data /dev/sdc
[root@compute ~]# mkdir -p /srv/node/sdc
[root@compute ~]# blkid -s UUID -o value /dev/sdc
[root@compute ~]# vi /etc/fstab
```

把上一条命令显示的UUID写入fstab，挂载点为/srv/node/sdc。

```config
UUID=<dev-sdc-uuid> /srv/node/sdc xfs noatime,nodiratime,logbufs=8 0 2
```

```command
[root@compute ~]# mount /srv/node/sdc
[root@compute ~]# chown -R swift:swift /srv/node
```

2．安装软件包并配置rsync

compute节点安装账户、容器、对象服务和rsync。三个Swift存储服务直接读写/srv/node/sdc，rsync则为副本复制和后台修复提供节点间的数据传输通道。

```command
[root@compute ~]# dnf -y install openstack-swift-account openstack-swift-container openstack-swift-object rsync
[root@compute ~]# mkdir -p /etc/swift /srv/node/sdc
[root@compute ~]# chown -R swift:swift /etc/swift /srv/node
[root@compute ~]# vi /etc/rsyncd.conf
```

```config
uid = swift
gid = swift
log file = /var/log/rsyncd.log
pid file = /var/run/rsyncd.pid
address = 192.168.234.150

[account]
max connections = 2
path = /srv/node/
read only = false
lock file = /var/lock/account.lock

[container]
max connections = 2
path = /srv/node/
read only = false
lock file = /var/lock/container.lock

[object]
```

4．启动存储服务

rsync应先于三类Swift存储服务启动，使后台复制进程能够访问对应模块。随后依次启动账户、容器和对象服务，compute节点便可以按Ring中记录的设备和端口接收代理服务转发的请求。

```command
[root@compute ~]# mkdir -p /var/cache/swift
[root@compute ~]# chown -R swift:swift /var/cache/swift /srv/node
[root@compute ~]# systemctl enable rsyncd openstack-swift-account openstack-swift-container openstack-swift-object
[root@compute ~]# systemctl start rsyncd
[root@compute ~]# systemctl start openstack-swift-account openstack-swift-container openstack-swift-object
```

六．启动controller代理服务

在controller调整Swift配置目录权限，并启动代理服务。

```command
[root@controller ~]# chown -R root:swift /etc/swift
[root@controller ~]# systemctl enable openstack-swift-proxy
[root@controller ~]# systemctl start openstack-swift-proxy
```
